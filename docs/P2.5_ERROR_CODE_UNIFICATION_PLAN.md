## 1. 目标规范

### 1.1 统一响应结构

#### 成功响应

```json
{
  "success": true,
  "message": "操作成功",
  "code": "OK",             // 业务码，字符串
  "data": {...},
  "request_id": "uuid",
  "timestamp": "ISO8601"
}
```

#### 错误响应

```json
{
  "success": false,
  "message": "错误描述",
  "code": "AUTH_401",       // 业务错误码，字符串
  "data": null,
  "request_id": "uuid",
  "timestamp": "ISO8601"
}
```

### 1.2 核心约束

1. **code 字段统一为字符串业务码**
   - 成功默认：`"OK"`（替换原来的 `"SUCCESS"`）
   - 错误示例：`"AUTH_400"`, `"AUTH_401"`, `"SYS_001"`, `"BIZ_001"` 等

2. **删除 error_code 字段**
   - 旧版：`{"success": false, "code": 400, "error_code": "AUTH_401"}`
   - 新版：`{"success": false, "code": "AUTH_401"}`

3. **HTTP 状态码仅通过 FastAPI status_code 控制**
   - 不在 JSON 响应体中包含 HTTP 数字状态码
   - 示例：`JSONResponse(status_code=401, content={...})`

4. **所有业务码必须引用 ERROR_CODES.md**
   - 禁止自创错误码
   - 如需新增，先在 ERROR_CODES.md 中定义

## 4. 自检步骤

### 4.1 代码检查

每完成一个阶段后执行：

```bash
# 1. 搜索所有 error_code 字段（应该全部删除）
grep -rn "error_code" backend/

# 2. 搜索所有 "SUCCESS" 字符串（应该改为 "OK"）
grep -rn '"SUCCESS"' backend/

# 3. 搜索所有数字 code（应该改为字符串）
grep -rn '"code":\s*[0-9]' backend/

# 4. 检查所有 HTTPException detail 结构
grep -rn 'HTTPException.*detail=' backend/
```

### 4.2 单元测试

```bash
# 运行响应格式测试
pytest backend/tests/test_response_format.py -v

# 运行认证测试
pytest backend/tests/test_auth_* -v

# 运行所有测试
pytest backend/tests/ -v
```

### 4.3 API 手动验证

```bash
# 1. 测试成功响应
curl http://localhost:8000/api/v1/health
# 预期：{"success": true, "code": "OK", ...}

# 2. 测试认证失败
curl http://localhost:8000/api/v1/me
# 预期：{"success": false, "code": "AUTH_400", ...}

# 3. 测试无效Token
curl -H "Authorization: Bearer invalid_token" http://localhost:8000/api/v1/me
# 预期：{"success": false, "code": "AUTH_401", ...}

# 4. 测试业务错误
curl -X POST http://localhost:8000/api/v1/projects \
  -H "Authorization: Bearer valid_token" \
  -H "Content-Type: application/json" \
  -d '{}'
# 预期：{"success": false, "code": "VALIDATION_001", ...}
```

## 6. 风险评估和回滚方案

### 6.1 破坏性变更

| 变更内容 | 影响范围 | 风险级别 |
|---------|---------|---------|
| `"SUCCESS"` → `"OK"` | 所有成功响应的客户端解析 | ⚠️ 中 |
| 删除 error_code 字段 | 依赖 error_code 的客户端代码 | ⚠️ 中 |
| 错误码值变更 | 错误处理逻辑 | ⚠️ 低 |

### 6.2 回滚方案

1. **Git 分支管理**
   ```bash
   # 创建功能分支
   git checkout -b feature/p2.5-error-code-unification

   # 如需回滚
   git checkout main
   git branch -D feature/p2.5-error-code-unification
   ```

2. **分阶段提交**
   - 每个阶段独立提交
   - 提交信息格式：`P2.5: [阶段名称] - [修改内容]`
   - 便于单独回滚某个阶段

3. **兼容性过渡期**（可选）
   - 保留旧版 `"SUCCESS"` 作为 `"OK"` 的别名（代码层面）
   - 前端客户端逐步迁移
   - 2-4周后删除旧版支持
