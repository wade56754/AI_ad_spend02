## 规则详细定义

### BR-DATA-001: 外键完整性

#### 业务场景
系统中的数据表通过外键建立关联关系，如日报关联账户、账户关联渠道等。所有外键引用必须指向真实存在的记录，确保数据关联的有效性和查询的正确性。

#### 详细约束
- 📌 **强制**: 所有外键字段必须引用已存在的记录
- 📌 **强制**: 外键类型必须与被引用主键完全一致
- 📌 **强制**: 外键命名规范：`<实体名>_id`（如 `project_id`, `user_id`）
- ❌ **禁止**: 插入引用不存在记录的外键值
- ❌ **禁止**: 删除被其他记录引用的父记录（除非级联或软删除）
- ✅ **允许**: 可空外键（如 `owner_id` 在账户未分配时为 NULL）

#### 外键类型规范
| 被引用表 | 主键类型 | 外键字段示例 |
|----------|----------|--------------|
| users | UUID | user_id, owner_id, created_by |
| projects | BIGINT | project_id |
| channels | BIGINT | channel_id |
| ad_accounts | BIGINT | ad_account_id |

#### 前置条件
- 数据状态: 被引用记录已存在
- 引用: DATA_SCHEMA.md v5.6 §1.2

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 引用不存在的记录 | `BIZ_002` | 404 | 引用的记录不存在 |
| 外键类型不匹配 | `DB_003` | 400 | 数据完整性约束违反 |
| 删除被引用记录 | `BIZ_001` | 400 | 记录被其他数据引用，无法删除 |

#### 代码引用
- Model: `backend/models/*.py`
- 约束: SQLAlchemy ForeignKey + ON DELETE RESTRICT

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | 创建有效外键 | project_id=存在的项目 | 成功 |
| T2 | 创建无效外键 | project_id=不存在 ID | `BIZ_002` |
| T3 | 删除被引用记录 | 删除有日报的账户 | `BIZ_001` |
| T4 | 可空外键为 NULL | owner_id=NULL | 成功 |

### BR-DATA-002: 时间戳必填

#### 业务场景
系统需要记录所有业务数据的创建时间和更新时间，用于审计追溯、数据分析和问题排查。时间戳字段由系统自动填充，禁止手动设置。

#### 详细约束
- 📌 **强制**: 所有业务表必须包含 `created_at` 字段
- 📌 **强制**: 需要跟踪更新的表必须包含 `updated_at` 字段
- 📌 **强制**: `created_at` 在记录创建时自动填充，不可修改
- 📌 **强制**: `updated_at` 在记录更新时自动刷新
- ❌ **禁止**: API 请求中手动设置时间戳字段
- ✅ **允许**: 审计日志表仅包含 `created_at`（审计记录不可修改）

#### 时间戳规范
| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| created_at | TIMESTAMPTZ | NOW() | 记录创建时间，不可修改 |
| updated_at | TIMESTAMPTZ | NOW() | 记录更新时间，自动刷新 |

#### 前置条件
- 系统环境: 数据库时区设置为 UTC
- 引用: DATA_SCHEMA.md v5.6 §1.1

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 手动设置 created_at | `BIZ_001` | 400 | 禁止手动设置创建时间 |
| 手动设置 updated_at | `BIZ_001` | 400 | 禁止手动设置更新时间 |
| 时间戳为空 | `SYS_001` | 500 | 系统时间戳填充失败 |

#### 代码引用
- Model: `backend/models/base.py`
- 实现: SQLAlchemy `server_default=func.now()`, `onupdate=func.now()`

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | 创建记录自动填充 | 不传时间戳 | created_at 自动填充 |
| T2 | 更新记录刷新时间 | 修改任意字段 | updated_at 自动刷新 |
| T3 | 手动设置 created_at | 请求体含 created_at | `BIZ_001` |
| T4 | 时间戳不可回退 | updated_at < 原值 | 被忽略 |

### BR-DATA-003: 金额精度

#### 业务场景
系统涉及大量财务数据（消耗、充值、余额、利润），金额精度直接影响财务核算的准确性。所有金额字段必须使用统一的精度规范，确保计算不丢失精度。

#### 详细约束
- 📌 **强制**: 所有金额字段使用 `DECIMAL(15,2)` 类型
- 📌 **强制**: 金额字段默认值为 `0.00`
- 📌 **强制**: 金额计算结果保留两位小数（四舍五入）
- ❌ **禁止**: 使用 FLOAT 或 DOUBLE 存储金额
- ❌ **禁止**: 金额精度超过 2 位小数（特殊场景除外）
- ✅ **允许**: 汇率字段使用 `DECIMAL(12,4)` 保留 4 位小数

#### 金额字段规范
| 字段类型 | 精度 | 示例字段 |
|----------|------|----------|
| 金额/消耗 | DECIMAL(15,2) | spend, amount, balance |
| 单价 | DECIMAL(15,2) | unit_price, cpl |
| 汇率/比率 | DECIMAL(12,4) | conversion_rate |

#### 前置条件
- 数据模型: 遵循 DATA_SCHEMA.md 金额规范
- 引用: DATA_SCHEMA.md v5.6 §1.1

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 金额精度不正确 | `VALIDATION_001` | 400 | 金额必须保留两位小数 |
| 金额值溢出 | `VALIDATION_001` | 400 | 金额超出允许范围 |
| 金额为负（非借贷） | `BIZ_101` | 400 | 金额不能为负数 |

#### 代码引用
- Model: `backend/models/*.py`
- 类型: `Column(Numeric(15, 2), default=Decimal('0.00'))`

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | 正常金额 | amount=1234.56 | 成功 |
| T2 | 超过两位小数 | amount=1234.567 | 四舍五入为 1234.57 |
| T3 | 金额为负 | amount=-100.00 | `BIZ_101`（余额场景） |
| T4 | 金额溢出 | amount=10^16 | `VALIDATION_001` |

### BR-DATA-004: 软删除原则

#### 业务场景
业务数据具有审计追溯要求，物理删除会导致历史数据丢失、关联断裂。系统采用软删除机制，通过 `deleted_at` 字段标记删除状态，保留完整的数据历史。

#### 详细约束
- 📌 **强制**: 业务数据仅允许软删除（设置 `deleted_at`）
- 📌 **强制**: 软删除后数据对普通查询不可见
- 📌 **强制**: 软删除数据保留外键完整性
- ❌ **禁止**: 物理删除业务数据（DELETE FROM）
- ❌ **禁止**: 软删除后修改业务字段
- ✅ **允许**: 日志表/临时表物理删除（非业务数据）
- ✅ **允许**: admin 恢复软删除数据（需审计）

#### 软删除机制
| 操作 | 实现方式 | 说明 |
|------|----------|------|
| 删除 | SET deleted_at = NOW() | 标记删除时间 |
| 查询 | WHERE deleted_at IS NULL | 默认过滤已删除 |
| 恢复 | SET deleted_at = NULL | 仅 admin 可操作 |

#### 前置条件
- 数据模型: 表包含 `deleted_at` 字段
- 引用: DATA_SCHEMA.md v5.6 §1.1

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 尝试物理删除 | `BIZ_001` | 400 | 禁止物理删除业务数据 |
| 操作已删除记录 | `BIZ_002` | 404 | 记录不存在或已删除 |
| 非 admin 恢复 | `AUTH_500` | 403 | 仅管理员可恢复删除记录 |

#### 代码引用
- Model: `backend/models/base.py`
- 实现: `deleted_at = Column(TIMESTAMPTZ, nullable=True)`

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | 软删除记录 | DELETE /projects/1 | deleted_at 被设置 |
| T2 | 查询过滤已删除 | GET /projects | 不含已删除记录 |
| T3 | 物理删除尝试 | 直接 SQL DELETE | `BIZ_001` |
| T4 | admin 恢复记录 | POST /projects/1/restore | 成功 + 审计 |

### BR-DATA-005: 枚举值校验

#### 业务场景
系统中存在大量枚举字段（角色、状态、类型），枚举值直接影响业务逻辑和权限判断。所有枚举字段必须在写入前校验合法性，防止非法值导致系统异常。

#### 详细约束
- 📌 **强制**: 所有枚举字段必须定义合法取值范围
- 📌 **强制**: 写入前必须校验枚举值合法性
- 📌 **强制**: 枚举值使用 snake_case 小写命名
- ❌ **禁止**: 接受未定义的枚举值
- ❌ **禁止**: 在代码中硬编码枚举值（必须引用常量）
- ✅ **允许**: 扩展枚举需同步更新 STATE_MACHINE.md

#### 核心枚举定义
| 枚举类型 | 合法取值 | 引用 |
|----------|----------|------|
| 技术角色 | admin, finance, data_operator, account_manager, media_buyer | STATE_MACHINE.md §2 |
| 账户状态 | new, testing, active, suspended, dead, archived | STATE_MACHINE.md §6 |
| 日报状态 | raw_submitted, trend_pending, trend_ok, ... | STATE_MACHINE.md §5 |
| 项目状态 | draft, active, suspended, archived | STATE_MACHINE.md §4 |

#### 前置条件
- 数据模型: 枚举定义在 STATE_MACHINE.md
- 引用: STATE_MACHINE.md v2.7 §4

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 非法枚举值 | `BIZ_001` | 400 | 无效的枚举值: {value} |
| 枚举字段为空 | `VALIDATION_001` | 400 | 枚举字段不能为空 |
| 状态流转非法 | `STATE_400` | 400 | 非法状态流转 |

#### 代码引用
- Enum: `backend/core/enums.py`
- 校验: Pydantic Enum validator

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | 合法枚举值 | role=admin | 成功 |
| T2 | 非法枚举值 | role=superuser | `BIZ_001` |
| T3 | 枚举为空 | role=null | `VALIDATION_001` |
| T4 | 非法状态流转 | draft → completed | `STATE_400` |
