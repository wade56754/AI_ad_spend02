## 第一章 业务第一性原则 (First Principles)

### 1.1 系统存在的唯一理由

本系统只服务广告投放业务价值链，不服务通用金融系统。

### 1.2 核心业务流程

#### 业务价值链

```
甲方（客户）─────→ 公司 ─────→ 代理商 ─────→ 广告平台（FB/TK）
     │              │            │               │
     ↓              ↓            ↓               ↓
   付款          转款          充值           消耗
     │              │            │               │
     ↓              ↓            ↓               ↓
  应收账款      代理余额      账户余额       广告效果
     │                           │               │
     └───────────────────────────┴───────────────┘
                        ↓
                    投手日报 (raw → final)
                        ↓
                    账本记录 (PROJECT + SUPPLIER)
```

#### 资金流向说明

| 流向 | 来源 | 去向 | 账本影响 |
|------|------|------|----------|
| 甲方付款 | 甲方银行账户 | 公司账户 | PROJECT +金额 |
| 公司转款 | 公司账户 | 代理商账户 | 待归因 |
| 代理充值 | 代理商账户 | 广告账户 | 账户余额 +金额 |
| 平台消耗 | 广告账户 | 广告平台 | SUPPLIER -金额 |

### 1.3 核心功能模块

本系统包含 **4 大核心模块**：

| 模块 | 管理对象 | 核心问题 |
|------|---------|---------|
| **投手管理** | 投手团队 | 谁在投？投得怎么样？ |
| **财务管理** | 资金流水 | 钱从哪来？花到哪去？ |
| **广告账号管理** | 广告账户 | 账户够用吗？状态正常吗？ |
| **项目管理** | 甲方项目 | 客户赚钱吗？ |

> 详细模块定义参见: `docs/1.overview/CORE_MODULES.md`

### 1.4 数据规模与增长预估

#### 现有数据规模

| 数据表 | 当前记录数 | 关键字段 |
|--------|-----------|---------|
| daily_reports | ~5,000 | 日期、投手、地区、平台、消耗、进粉 |
| ledger | ~10,000 | 交易类型、金额、状态、归属 |
| ad_accounts | ~400 | 账户ID、代理商、平台、状态 |
| projects | ~100 | 项目名、甲方、单价、状态 |

#### 年增量预估

| 数据表 | 年增量 | 增长因素 |
|--------|-------|---------|
| ledger | ~100,000条/年 | 每日报产生1-2条 |
| daily_reports | ~15,000条/年 | 投手数 × 工作日 |
| platform_imports | ~70,000条/年 | 每账户每日1条 |

### 1.5 不可改变的业务真理

**FP-01 平台是观测者，不是控制者**

广告账户由外部平台管理，本系统无控制权。
平台只能观测、记录、响应账户状态变化，不能创造或逆转。

> 引用: MASTER.md INV-003「日报状态单向流转」

**FP-02 收益归属由投放行为决定，不由协商决定**

收益归属逻辑仅根据：
- 投放行为发生顺序
- 平台返回数据

不因角色意愿、口头描述、事后协商而改变。

**FP-03 账务是时间序列，不是状态**

> 引用: MASTER.md INV-001「账务只追加，不修改」

**FP-04 死亡不可逆转**

账户死亡是终态。
业务可通过迁移能力（C-06）转移，原账户不可复活。

### 1.3 系统边界声明

本系统不会：
- 成为通用财务系统
- 接管第三方平台账户控制权

> 注: 行为禁令详见第八章「Prohibited」

## 第二章 业务不可变量 (Business Invariants)

业务不可变量 = 无论系统如何演进，永远为真的业务事实。
违反任一条 = 业务逻辑错误，不是技术 bug。

### BI-01 账务记录不可篡改

已锁定（final_locked）的账务记录：
- 不可修改金额
- 不可修改归属
- 不可删除

错误修正唯一方式：红冲（REVERSAL）。

> 引用: MASTER.md INV-001, LEDGER_SOT.md §3, STATE_MACHINE.md §8.1

### BI-02 广告账户生命周期不可回溯

广告账户状态变化是单向的：
- 正常账户可能变为受限
- 受限账户可能变为死号
- 死号永远是死号

死号业务可迁移至新账户，原账户不可复活。

> 引用: STATE_MACHINE.md §7.1 账户生命周期

### BI-03 收益归属不可重分配

投手已确认的收益归属：
- 不因事后协商而改变
- 不因团队调整而转移
- 不因项目变更而重算

对账错误唯一修正方式：红冲后重新归属。

> 引用: BUSINESS_RULES.md BR-RPT-005「终态不可回退」

### BI-04 账务必须源于日报

账务记录的唯一合法来源是已锁定（final_locked）的日报。

以下不能直接成为账务：
- Excel 导入数据
- 截图或口头描述
- 第三方平台打款通知

> 引用: DAILY_REPORT_SOT.md §1, STATE_MACHINE.md §8

### BI-05 角色职责不可越界

每个角色只能操作其职责范围内的业务对象：
- 投手：提交投放数据
- 运营：审核与确认
- 财务：结算与对账

职责边界由 MASTER.md INV-004 定义，不可局部覆盖。

> 引用: AUTH_SPEC.md §5

## 第三章 业务能力 (Capabilities)

业务能力 = 系统对外提供的价值交付单元。
能力不是模块，不是 API，不是 CRUD。
每项能力定义：输入（业务触发）→ 输出（业务结果）。

### C-01 日报提交能力

**业务价值**: 投手将每日投放数据提交至系统。

- 输入：投手填写的 raw 数据（粉数、消耗）
- 输出：待审核的日报记录

> 引用: STATE_MACHINE.md §8「raw_submitted」

### C-02 趋势风控能力

**业务价值**: 系统自动识别异常投放数据。

- 输入：已提交的 raw 数据
- 输出：风控判定结果（通过 / 标记异常）

> 引用: BUSINESS_RULES.md BR-TREND-001, BR-TREND-002

### C-03 日报确认能力

**业务价值**: 运营审核并确认最终计费数据。

- 输入：已通过风控的日报 + 运营录入的 real/final 数据
- 输出：可计费的日报记录

> 引用: STATE_MACHINE.md §8「final_confirmed」

### C-04 账务生成能力

**业务价值**: 系统根据已确认日报生成账本记录。

- 输入：已锁定（final_locked）的日报
- 输出：收入账本记录（PROJECT）+ 成本账本记录（SUPPLIER）

> 引用: MASTER.md INV-001, LEDGER_SOT.md §2

### C-05 红冲修正能力

**业务价值**: 财务修正已锁定的错误账务。

- 输入：错误日报 + 外部审批单号
- 输出：反向账务记录（REVERSAL）

约束：原记录不可修改，仅追加反向事件。

> 引用: MASTER.md INV-003「红冲机制」, LEDGER_SOT.md §3

### C-06 死号迁移能力

**业务价值**: 将死亡账户的存续业务转移至新账户。

- 输入：死亡账户 + 新目标账户
- 输出：迁移记录 + 账务影响说明

约束：原账户永久冻结，不可复活。

> 引用: TRANSFER_SOT.md §1, STATE_MACHINE.md §7.1

## 第四章 利益相关者 (Stakeholders)

### 4.1 角色清单 (7角色)

| 角色ID | 中文名 | 职责范围 | 核心模块权限 |
|--------|-------|---------|-------------|
| pitcher | 投手 | 操作广告账户，每日填报消耗和效果 | 投手管理：填报日报 |
| account_manager | 户管 | 管理广告账户分配 | 账号管理：全部功能 |
| supervisor | 主管 | 确认日报、审核数据 | 投手管理：审核；项目管理：单价配置 |
| project_owner | 项目负责人 | 项目盈亏、资金使用效率、团队协调 | 项目管理：全部功能；充值申请 |
| finance | 财务 | 管理资金流水、对账、冲正 | 财务管理：全部功能 |
| ceo | CEO | 查看报表、关账审批 | 全模块：查看；财务管理：关账 |
| admin | 管理员 | 系统配置（不参与业务操作） | 基础数据维护 |

### 4.2 角色与模块权限矩阵

| 角色 | 投手管理 | 财务管理 | 账号管理 | 项目管理 |
|------|---------|---------|---------|---------|
| pitcher | 填报日报 | - | - | - |
| account_manager | 查看绩效 | - | 全部功能 | - |
| supervisor | 审核日报、绩效看板 | - | 查看 | 单价配置 |
| project_owner | 查看绩效 | 申请充值 | 查看 | 全部功能 |
| finance | - | 全部功能 | 查看 | 查看 |
| ceo | 绩效看板 | 关账审批、报表 | 查看 | 利润分析 |
| admin | 投手信息 | - | 代理商管理 | 甲方管理 |

### 4.3 约束声明

- 角色权限边界由 MASTER.md INV-004 和 AUTH_SPEC.md 定义
- 禁止单一用户同时拥有 pitcher 和 supervisor 角色
- 禁止单一用户同时拥有 supervisor 和 finance 角色
- finance 执行冲正必须提供外部审批单号

> 详细权限规则参见: AUTH_SPEC.md §5

## 第五章 业务约束 (Business Constraints)

本章定义业务结构级约束，不包含工程约束。
技术约束定义于 ARCHITECTURE.md。

### 5.1 业务边界约束

本系统的服务边界：
- 仅服务广告投放业务价值链
- 不服务通用财务、税务、第三方代理场景
- 不控制外部广告平台账户

> 引用: 第一章 FP-01, 1.3 系统边界声明

### 5.2 合规约束

账务合规要求（详见第二章业务不可变量）：
- BI-01: 账务记录不可篡改
- BI-04: 账务必须源于日报
- BI-05: 角色职责不可越界

> 引用: MASTER.md INV-001, INV-004

### 5.3 风险容忍度

| 风险类型 | 容忍度 | 说明 |
|---------|-------|------|
| 账务记录缺失 | 0 | 不允许 |
| 审计链断裂 | 0 | 不允许 |
| 终态数据篡改 | 0 | 不允许 |

> 引用: MASTER.md 第一章 1.2 核心风险

- 禁止策略实验

Freeze 是治理机制，不是建议。

## 第八章 Prohibited（永远禁止）

本章定义业务宇宙维度的禁止行为，不因版本迭代而改变。
违反任一条 = 合规违规 = 审计风险。

### D-01 手动改写账务历史

禁止：
- 修改已有 LedgerEntry
- 人工覆盖账务
- 删除账务记录

> 引用: MASTER.md INV-001「审计不可逆」, BI-01

### D-02 跳过日报直入账本

禁止：
- 绕过 DailyReport 直接写 Ledger
- Excel 导入自动生成 entry

> 引用: BI-04「账务必须源于日报」

### D-03 将死号标记为恢复

禁止：
- 关闭迁移流程直接复用原账号
- 直接在原账号上继续业务

> 引用: FP-04「死亡不可逆转」, BI-02

### D-04 未审计数据做决策

禁止：
- 根据截图/口头信息修改收益
- 用非系统数据触发结算

> 引用: MASTER.md INV-002「三数据流职责分离」

### D-05 事后重分配收益

禁止：
- 项目层面强制改投手收益
- 事后佣金策略修订影响历史记录

> 引用: FP-02, BI-03「收益归属不可重分配」

### D-06 业务试验进入正式账本

禁止：
- A/B 实验直接写 final ledger
- 非生产数据进入结算闭环

> 引用: MASTER.md INV-003「终态保护」
