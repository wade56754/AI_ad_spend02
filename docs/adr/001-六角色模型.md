# ADR-001: 采用6角色模型

> **状态**: accepted
> **日期**: 2025-12-22 (初始), 2025-12-30 (更新)
> **决策者**: 架构组
> **关联**: MASTER.md v4.9

---

## 背景

**问题陈述**:
- 早期设计使用5角色模型（admin, finance, data_operator, account_manager, media_buyer）
- 业务发展后发现角色职责不清晰，特别是"谁对项目盈亏负责"
- data_operator和account_manager职责重叠

**约束条件**:
- 必须支持三权分立：审批权、执行权、监督权
- 必须能清晰回答"谁对钱负责、谁对结果负责、谁能纠偏"
- 需要向前兼容现有用户数据

---

## 决策

**我们决定**: 采用6角色模型 (MASTER.md v4.9 §2.4)

| 角色 | 职责 | 数据域 |
|------|------|-------|
| ceo | 资金安全、最终决策、月结确认 | 全局 |
| project_owner | 项目盈亏、资金使用效率、日常监督 | 自己项目 |
| finance | 资金出入准确、对账 | 财务数据 |
| pitcher | CPL达标、日报准确 | 自己账户 |
| account_manager | 账户分配、状态监控 | 分配账户 |
| admin | 系统配置（不参与业务） | 系统配置 |

> ⚠️ **废弃角色**: `supervisor` 已废弃 (PRD v5.1)，其职责已合并到 `project_owner`

---

## 备选方案

### 方案A: 保持5角色
- **优点**: 无需迁移
- **缺点**: 职责不清晰
- **结论**: ❌ 不采用

### 方案B: 7角色模型（曾采纳，现废弃）
- **优点**: 三权清晰、职责明确
- **缺点**: supervisor 与 project_owner 职责重叠
- **结论**: ⚠️ v1.0 采用，v1.1 废弃

### 方案C: 6角色模型（当前采纳）
- **优点**: 精简高效、职责清晰、减少角色混淆
- **缺点**: 需迁移 supervisor 用户
- **结论**: ✅ 采用

### 方案D: 9角色模型
- **优点**: 更细粒度
- **缺点**: 过于复杂
- **结论**: ❌ 不采用

---

## 影响

### 正面影响
- 职责清晰，便于问责
- 数据域隔离，安全性提升
- 符合实际业务组织结构
- 减少角色数量，降低复杂度

### 负面影响
- 需要迁移现有用户数据（一次性工作）

### 受影响的组件
- AUTH_SPEC.md: 权限矩阵更新
- 数据库users表: role字段值更新
- 前端权限判断: 角色名更新
- DATA_SCHEMA.md: CHECK约束更新

---

## 实施

### 迁移映射
| 旧角色 | 新角色 |
|--------|--------|
| admin | admin |
| finance | finance |
| data_operator | account_manager |
| account_manager | project_owner |
| media_buyer | pitcher |
| supervisor | project_owner (PRD v5.1) |
| - | ceo (新增) |

### 迁移脚本
```sql
-- v1.0: 初始迁移 (5角色→7角色)
UPDATE users SET role = 'account_manager' WHERE role = 'data_operator';
UPDATE users SET role = 'project_owner' WHERE role = 'account_manager';
UPDATE users SET role = 'pitcher' WHERE role = 'media_buyer';

-- v1.1: supervisor废弃 (7角色→6角色)
UPDATE users SET role = 'project_owner' WHERE role = 'supervisor';
```
