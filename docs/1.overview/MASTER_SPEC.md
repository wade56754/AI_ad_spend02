## 1. 系统定位

### 1.1 系统本质

AI 广告代投系统是以**项目 (国家/地区)** 为核心的**资金结算与数据审计系统**，管理三个核心流程：

1. **投放流程**: 投手 → 日报提交 → 趋势风控 → 最终粉确认
2. **资金流程**: 客户充值 → 项目余额 → 粉数计费 → 成本扣费
3. **审计流程**: 原始数据 → 真实数据 → 最终数据 → 红冲修正

### 1.2 核心业务原则

| 原则 | 说明 | 强制性 |
|-----|------|--------|
| **项目即业务单元** | 国家 = 地区 = 项目，所有业务围绕项目展开 | 🔴 强制 |
| **最终粉唯一计费** | `conversions_final` 是计费唯一来源 | 🔴 强制 |
| **真实消耗唯一成本** | `real_spend + fee` 是成本唯一来源 | 🔴 强制 |
| **双账本独立核算** | 项目余额与供应商余额两套账本，不得混合 | 🔴 强制 |
| **终态数据不可变** | `final_locked` 后仅可通过红冲修正 | 🔴 强制 |

### 1.3 解决的核心问题

| 问题 | 架构解决方案 |
|-----|------------|
| 粉数数据不可信 | 三数据流分离 (raw/real/final) + 趋势风控 |
| 成本与收入混乱 | 双账本架构 (PROJECT/SUPPLIER) |
| 审批流程混乱 | 状态机驱动 + 职责分离 (SOD) |
| 数据篡改风险 | 终态保护 + 红冲机制 + 审计日志 |
| 权限管理失控 | 5 大角色固定 + Service 层数据隔离 |

## 3. 核心设计原则

### 3.1 三数据流架构

**设计理念**: 分离投手提交数据、真实消耗数据、最终计费数据，确保计费准确性与可追溯性。

```
投手提交 (raw)  →  趋势风控  →  运营录入 (real)  →  最终确认 (final)  →  计费锁定
     ↓                                    ↓                    ↓
 不计费不计成本                        成本唯一来源          收入唯一来源
```

**核心约束**:
- ✅ `conversions_final` 计费: `revenue = conversions_final × unit_price`
- ✅ `real_spend` 计成本: `cost = real_spend + fee`
- ❌ 禁止使用 `conversions_raw` 或 `raw_spend` 计费/计成本
- ❌ 禁止跳过 `final` 直接计费

**详细规范**: STATE_MACHINE.md 第 8 章

### 3.2 双账本架构

**设计理念**: 项目收入与供应商成本独立核算，避免混淆，确保财务清晰。

```
PROJECT Ledger (项目收入账本)           SUPPLIER Ledger (供应商成本账本)
    ├─ 客户充值                             ├─ 财务充值
    ├─ 粉数计费收入 (REVENUE)                ├─ 真实消耗成本 (COST)
    ├─ 红冲修正 (REVERSAL)                   ├─ 死号迁移 (TRANSFER_IN/OUT)
    └─ 项目余额 (project.balance)            └─ 供应商余额 (supplier.balance)
```

**核心约束**:
- ✅ 两套账本独立，`ledger_type` 强制区分
- ✅ 同供应商内可直接迁移余额
- ❌ 禁止跨供应商直接迁移 (必须拆分为退款 + 充值)
- ❌ 禁止 PROJECT 账本记录 COST

**详细规范**: LEDGER_SOT.md

### 3.3 职责分离 (SOD)

**设计理念**: 防止内部欺诈，关键业务流程的申请人、审核人、审批人必须不同。

| 业务流程 | SOD 规则 | 强制性 |
|---------|---------|--------|
| 日报审核 | 提交人 ≠ 审核人 | 🔴 强制 |
| 充值审批 | 申请人 ≠ 审核人 ≠ 审批人 | 🔴 强制 |
| 对账确认 | 提交人 ≠ 确认人 | 🔴 强制 |

**详细规范**: BUSINESS_RULES.md BR-FIN-002

### 3.4 终态保护

**设计理念**: 已计费数据不可篡改，修正必须可追溯。

| 终态 | 保护机制 | 修正方式 |
|-----|---------|---------|
| `final_locked` (日报) | 不可回退、不可修改 | 红冲 (REVERSAL) |
| `archived` (项目) | 仅 admin 可回退 | [AUDIT] 强制 |
| `completed` (充值) | 仅 admin 可回退 | [AUDIT] 强制 |

**详细规范**: STATE_MACHINE.md 第 14.2 章

**固定角色**: `admin` / `finance` / `data_operator` / `account_manager` / `media_buyer`

**核心约束**:

## 7. 全局开发约束

### 7.1 命名规则

| 对象 | 规则 | 示例 | 禁止 |
|-----|------|------|------|
| 表名 | 小写复数 snake_case | `users`, `daily_reports` | `User`, `DailyReport` |
| 主键 | 固定 `id` | `id` | `user_id`, `pk` |
| 外键 | `<实体名>_id` | `project_id` | `project`, `projectId` |
| 布尔字段 | `is_*` / `has_*` | `is_active` | `active` |
| Model 类 | PascalCase 单数 | `User`, `DailyReport` | `user` |
| 函数 | snake_case 动词 | `get_current_user` | `getCurrentUser` |

### 7.2 数据类型约束

| 场景 | 数据库类型 | 应用层类型 | 前端类型 | 强制性 |
|-----|-----------|-----------|---------|--------|
| **时间** | `TIMESTAMPTZ` | `datetime (UTC)` | `Date` | 🔴 强制 |
| **金额** | `DECIMAL(15,2)` | `Decimal` | `string` | 🔴 强制 |
| **主键 (跨系统)** | `UUID` | `UUID` | `string` | 🔴 强制 |
| **主键 (业务表)** | `BIGSERIAL` | `int` | `number` | 🔴 强制 |
| **状态** | `VARCHAR(20)` | `Literal[...]` | `enum` | 🔴 强制 |

### 7.3 禁止事项

| 禁止行为 | 原因 | 违规错误码 |
|---------|------|-----------|
| 使用 `FLOAT`/`DOUBLE` 存储金额 | 精度丢失 | - |
| 使用 `TIMESTAMP` (无时区) | 时区混乱 | - |
| 使用 `datetime.now()` (本地时区) | 时区不一致 | - |
| 前端使用 `number` 类型传输金额 | 精度丢失 | - |
| 直接 `UPDATE` 状态字段 | 绕过状态机 | `STATE_400` |
| 直接 `UPDATE`/`DELETE` 终态数据 | 数据篡改 | `STATE_402` |
| 前端传递 `user_id` | 身份伪造 | `AUTH_500` |
| 前端解析 JWT Payload | 无法验证签名 | - |

## 8. 事务与并发

### 8.1 事务边界原则

| 场景 | 事务策略 | 强制性 |
|-----|---------|--------|
| **计费流程** | `SELECT ... FOR UPDATE` 锁定项目 | 🔴 强制 |
| **充值到账** | 唯一约束 `request_no UNIQUE` | 🔴 强制 |
| **死号迁移** | 同供应商内锁定账户 | 🔴 强制 |
| **红冲修正** | 独立事务 | 🔴 强制 |

**详细规范**: LEDGER_SOT.md, BUSINESS_RULES.md BR-FIN-005

### 8.2 并发控制

| 场景 | 策略 | 实现 |
|-----|------|------|
| 项目余额扣减 | 悲观锁 | `SELECT ... FOR UPDATE` |
| 充值到账 | 唯一约束 + 幂等性 | `request_no UNIQUE` |
| 日报提交 | 唯一约束 | `UNIQUE (report_date, ad_account_id)` |

## 9. 安全原则

### 9.1 Zero Trust

**核心理念**: 永远不信任客户端传来的用户身份信息

| 原则 | 强制性 |
|-----|--------|
| 从 Token 提取 `user_id`，禁止前端传递 | 🔴 强制 |
| Service 层验证数据归属 | 🔴 强制 |
| 后端验证角色权限 | 🔴 强制 |
| 禁止前端解析 JWT Payload | 🔴 强制 |

**详细规范**: AUTH_SPEC.md 第 9 章

### 9.2 RLS 策略

- 数据库 RLS: ❌ 当前版本未启用 (`ENABLE_RLS=false`)
- 应用层 RBAC: ✅ 已启用 (Service 层 + `@require_role` 装饰器)
- 未来规划: 📘 规划启用 RLS 作为双重保护（详见 RLS_POLICIES_SOT.md v2.1）

**当前安全策略**:
- Service 层权限校验（强制执行）
- 数据访问必须通过 Service 层（禁止直接查询数据库）
- 角色权限验证通过 `@require_role` 装饰器实现
