# 提示词问题诊断参考

## 快速诊断清单

当提示词效果不佳时，按以下顺序检查：

| 检查项 | 问题表现 | 解决方案 |
|--------|----------|----------|
| 1. 任务不清 | Claude 输出偏离预期 | 明确任务目标和成功标准 |
| 2. 上下文不足 | Claude 做出错误假设 | 补充必要背景信息 |
| 3. 示例缺失 | 输出格式/风格不一致 | 添加 3-5 个具体示例 |
| 4. 边界模糊 | Claude 过度发挥或遗漏 | 明确禁止事项和必须事项 |
| 5. 步骤过多 | Claude 遗漏中间步骤 | 拆解为链式提示词 |
| 6. 角色不当 | 专业深度不够 | 定义更具体的专业角色 |

## 问题分类与处理

### STRUCT（结构问题）

**症状**：
- Claude 混淆了指令和示例
- 输出格式混乱
- 关键信息被忽略

**诊断**：
```
□ 是否使用 XML 标签分隔不同部分？
□ 标签命名是否一致？
□ 嵌套层级是否合理（≤3 层）？
□ 是否在指令中引用标签名称？
```

**修复**：
```xml
<!-- 修复前 -->
请分析以下数据并生成报告。数据包括...
报告格式应该是...
注意事项：不要...

<!-- 修复后 -->
<task>分析数据并生成报告</task>

<data>
[数据内容]
</data>

<output_format>
[报告格式要求]
</output_format>

<constraints>
[注意事项]
</constraints>
```

### ROLE（角色问题）

**症状**：
- 回答过于泛泛
- 专业深度不够
- 语气/风格不符合预期

**诊断**：
```
□ 是否定义了角色？
□ 角色是否足够具体（职位 + 领域 + 经验）？
□ 角色是否与任务匹配？
□ 是否定义了工作风格？
```

**修复**：
```xml
<!-- 修复前 -->
<s>你是一个助手。</s>

<!-- 修复后 -->
<s>
你是一位资深 Facebook 广告投放优化师，
拥有 5 年以上代投经验，专精于电商类客户。
你熟悉账户健康度评估、预算分配策略、素材 A/B 测试。
你的分析风格是：数据驱动、结论先行、建议可执行。
</s>
```

### EXAMPLE（示例问题）

**症状**：
- 输出格式不稳定
- 风格忽高忽低
- 边界情况处理不当

**诊断**：
```
□ 是否提供了示例？
□ 示例数量是否足够（3-5 个）？
□ 示例是否覆盖了常见情况？
□ 示例是否包含边界情况？
□ 是否同时提供正面和负面示例？
```

**修复**：
```xml
<!-- 添加多样化示例 -->
<examples>
  <example type="good" scenario="normal">
    <input>用户提交日报，数据完整</input>
    <output>状态更新为 pending_review</output>
  </example>
  
  <example type="good" scenario="edge">
    <input>用户提交日报，CPA 异常高（>$50）</input>
    <output>状态更新为 pending_review，同时触发 AI 预警</output>
  </example>
  
  <example type="bad" scenario="error">
    <input>用户提交日报，缺少必填字段</input>
    <output>❌ 不应接受并静默处理</output>
    <correct>应返回 400 错误，明确指出缺失字段</correct>
  </example>
</examples>
```

### AMBIG（歧义问题）

**症状**：
- Claude 反复询问澄清
- 不同次运行结果差异大
- Claude 自行做出假设

**诊断**：
```
□ 判断标准是否明确？
□ 是否有多种合理解读？
□ 术语是否有歧义？
□ 条件分支是否清晰？
```

**修复**：
```xml
<!-- 修复前 -->
<rule>过时的文档应该归档</rule>

<!-- 修复后 -->
<rule>
过时文档的判断标准：
1. 版本号低于当前 freeze 版本（如 v2.5 < v2.6）
2. 内容已被 freeze 文档完全覆盖
3. frontmatter 中 status = deprecated
4. 超过 6 个月未更新且无任何引用

满足以上任一条件即视为过时，应归档至 docs/archive/
</rule>
```

### SCOPE（范围问题）

**症状**：
- Claude 做了不该做的事
- Claude 遗漏了该做的事
- 输入输出格式不明

**诊断**：
```
□ 是否明确了输入格式和来源？
□ 是否明确了输出格式和位置？
□ 是否明确了任务边界？
□ 是否区分了必做/可选/禁止？
```

**修复**：
```xml
<!-- 添加明确的范围定义 -->
<scope>
  <input>
    <source>用户上传的 Excel 文件</source>
    <format>xlsx，包含 date, spend, clicks, conversions 列</format>
    <validation>自动校验列名和数据类型</validation>
  </input>
  
  <output>
    <format>JSON 对象</format>
    <location>返回给调用方，不写入文件</location>
  </output>
  
  <boundaries>
    <must>计算 CPA 和 ROAS</must>
    <must>标记异常数据点</must>
    <may>提供优化建议</may>
    <must_not>修改原始文件</must_not>
    <must_not>调用外部 API</must_not>
  </boundaries>
</scope>
```

### CHAIN（复杂度问题）

**症状**：
- Claude 跳过中间步骤
- 长任务中后期质量下降
- 无法追踪问题出在哪一步

**诊断**：
```
□ 任务是否涉及 3 个以上独立步骤？
□ 中间结果是否需要验证？
□ 是否有条件分支？
□ 单次输出是否超过 4000 tokens？
```

**修复**：
参见 references/chain-patterns.md，将任务拆解为链式提示词。

## 调试策略

### 1. 最小化复现

将提示词精简到最小可复现问题的版本，隔离问题根因。

### 2. 逐步添加

从最简单的提示词开始，逐步添加组件，观察何时出现问题。

### 3. 对比测试

准备 A/B 两个版本，对同一输入进行测试，对比输出差异。

### 4. 边界测试

使用边界条件输入（空值、极大值、异常格式）测试提示词健壮性。

## 常见陷阱

| 陷阱 | 描述 | 避免方法 |
|------|------|----------|
| 隐式假设 | 假设 Claude 知道项目背景 | 明确提供所有必要上下文 |
| 过度工程 | 为简单任务设计复杂提示词 | 先用简单提示词，按需迭代 |
| 示例过拟合 | 示例太相似，缺乏多样性 | 确保示例覆盖不同场景 |
| 规则冲突 | 多条规则相互矛盾 | 明确优先级或消除冲突 |
| 输出过长 | 期望单次生成过多内容 | 拆分任务或限制输出长度 |
