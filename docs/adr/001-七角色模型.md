## 背景

**问题陈述**:
- 早期设计使用5角色模型（admin, finance, data_operator, account_manager, media_buyer）
- 业务发展后发现角色职责不清晰，特别是"谁对项目盈亏负责"
- data_operator和account_manager职责重叠
- 缺少"主管"这一日常监督角色

**约束条件**:
- 必须支持三权分立：审批权、执行权、监督权
- 必须能清晰回答"谁对钱负责、谁对结果负责、谁能纠偏"
- 需要向前兼容现有用户数据

---

## 决策

**我们决定**: 采用7角色模型

| 角色 | 职责 | 数据域 |
|------|------|-------|
| ceo | 资金安全、最终决策、月结确认 | 全局 |
| project_owner | 项目盈亏、资金使用效率 | 自己项目 |
| finance | 资金出入准确、对账 | 财务数据 |
| supervisor | 团队产出、日常监督 | 团队数据 |
| pitcher | CPL达标、日报准确 | 自己账户 |
| account_manager | 账户分配、状态监控 | 分配账户 |
| admin | 系统配置（不参与业务） | 系统配置 |

---

## 备选方案

### 方案A: 保持5角色
- **优点**: 无需迁移
- **缺点**: 职责不清晰
- **结论**: ❌ 不采用

### 方案B: 7角色模型（采纳）
- **优点**: 三权清晰、职责明确
- **缺点**: 需要迁移现有用户
- **结论**: ✅ 采用

### 方案C: 9角色模型
- **优点**: 更细粒度
- **缺点**: 过于复杂
- **结论**: ❌ 不采用

---

## 影响

### 正面影响
- 职责清晰，便于问责
- 数据域隔离，安全性提升
- 符合实际业务组织结构

### 负面影响
- 需要迁移现有用户数据（一次性工作）

### 受影响的组件
- AUTH_SPEC.md: 权限矩阵更新
- 数据库users表: role字段值更新
- 前端权限判断: 角色名更新

## 实施

### 迁移映射
| 旧角色 | 新角色 |
|--------|--------|
| admin | admin |
| finance | finance |
| data_operator | account_manager |
| account_manager | project_owner |
| media_buyer | pitcher |
| - | supervisor (新增) |
| - | ceo (新增) |

### 迁移脚本
```sql
UPDATE users SET role = 'account_manager' WHERE role = 'data_operator';
UPDATE users SET role = 'project_owner' WHERE role = 'account_manager';
UPDATE users SET role = 'pitcher' WHERE role = 'media_buyer';
```
