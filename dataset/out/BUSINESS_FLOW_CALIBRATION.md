## 一、总体判断（结论先行）

**结论：作为业务认知稿基本合格，但作为系统设计依据需要重大校准。**

| 评估维度 | 得分 | 说明 |
|----------|------|------|
| 业务主线 | ✓ 80% | 角色、流程、数据关系基本正确 |
| 现实适配 | ✗ 40% | 过于理想化，未体现"脏数据"和"模糊边界" |
| 系统可落地 | ✗ 30% | 多处假设不成立，直接实现会翻车 |

**核心问题：**
1. 假设数据完整且可自动计算 — **现实：数据残缺，需人工补充**
2. 假设对账有明确的"准" — **现实：两个来源都有问题，需人工裁决**
3. 假设结算有固定周期 — **现实：周期弹性，可跨期调整**
4. 假设项目/账户/投手映射清晰 — **现实：边界模糊，多对多**

## 三、被理想化的流程节点（风险点说明）

### 3.1 ⚠️ 账户准备流程

**原文描述：**
```
选择代理商 → 充值开户 → 分配账户 → 投手领用绑定项目
```

**现实问题：**
| 问题 | 数据证据 |
|------|----------|
| 账户-投手不是1:1 | 同一 platform_id 出现在多个投手记录中 |
| 账户-项目关系模糊 | 账户表无 project_id 字段 |
| 费率表不存在 | 代理商费率需人工维护 |

**系统风险：** 如果强制绑定，会导致数据无法录入。

---

### 3.2 ⚠️ 日常投放流程

**原文描述：**
```
AM 9:00 登录 → AM 10:00 分析 → 全天投放 → PM 6:00 填日报 → PM 8:00 导出消耗
```

**现实问题：**
| 问题 | 数据证据 |
|------|----------|
| 时间不固定 | daily_report 的时间戳分散在全天 |
| 存在漏填/补填 | 同一天有多条记录，或某些天无记录 |
| 导出不是每天 | ad_spend_daily 可能多天一批导入 |

**系统风险：** 如果强制每日提交，会被绕过或产生虚假数据。

---

### 3.3 ⚠️ 数据对账流程

**原文描述：**
```
对账原则：
- 消耗金额：以 ad_spend_daily.actual_spend 为准
- 手续费：actual_spend × 代理商费率
- 总成本：actual_spend + fee
```

**现实问题：**
| 问题 | 数据证据 |
|------|----------|
| actual_spend 可能为空 | 部分记录 actual_spend = NaN |
| 费率表不存在 | 无法自动计算手续费 |
| fee 是人工填报的 | 与"消耗×费率"不一定相等 |
| 两个来源都可能有错 | 不能简单"以谁为准" |

**系统风险：** 自动计算会产生错误数据，且用户无法纠正。

---

### 3.4 ⚠️ 月度结算流程

**原文描述：**
```
月初 1-3日：
① 汇总上月消耗
② 核对客户付款
③ 计算项目毛利
④ 输出月度报表
```

**现实问题：**
| 问题 | 数据证据 |
|------|----------|
| 结算周期不固定 | 部分项目备注"跨月结算" |
| 收入确认有争议 | "应收未收"数据存在 |
| 预付款跨项目 | 备注："预付款是一起的" |
| 可能需要调整 | 存在历史月份数据修改 |

**系统风险：** 固定周期+自动锁定会导致无法处理例外情况。

---

### 3.5 ⚠️ KPI 计算

**原文描述：**
```
CPL = 消耗 / 进粉数
毛利 = 收入 - 支出
```

**现实问题：**
| 问题 | 数据证据 |
|------|----------|
| 进粉数来源不唯一 | 可能来自日报、也可能来自客户反馈 |
| #DIV/0! 错误 | 进粉数为0时计算失败 |
| 收入确认时点不固定 | 预付款、账期混杂 |

**系统风险：** 自动计算的 KPI 可能误导决策。

## 四、系统可落地的校准建议

### 4.1 账户准备流程校准

| 原流程 | 校准后 |
|--------|--------|
| 账户绑定投手 | → 账户与投手建立"使用记录"，不做强绑定 |
| 账户绑定项目 | → 账户增加"项目标签"，允许多标签 |
| 代理商费率表 | → 费率表可选填，系统不依赖它做自动计算 |

**校准后流程：**
```
代理商录入（人工）→ 账户录入（导入）→ 使用时关联投手（自动记录）
                                      ↓
                              项目标签（可选，人工打标）
```

---

### 4.2 日常投放流程校准

| 原流程 | 校准后 |
|--------|--------|
| 固定时间点 | → 删除时间约束，改为"发生即记录" |
| 当日必填 | → 允许补录历史日期，标记"补录" |
| 当日导出 | → 允许批量导入多日数据 |

**校准后流程：**
```
投手填报日报 ──→ 记录（report_date + submit_date）
                  ↓
              submit_date ≠ report_date → 标记"补录"

平台消耗导入 ──→ 批量导入（保留原始日期）
                  ↓
              import_date 字段记录导入时间
```

---

### 4.3 数据对账流程校准

| 原流程 | 校准后 |
|--------|--------|
| 以 ad_spend_daily 为准 | → 系统展示两个来源，人工选择采信值 |
| 手续费 = 消耗 × 费率 | → 默认取原始 fee 字段，允许人工覆盖 |
| 自动计算总成本 | → 展示计算值，但需人工确认 |

**校准后流程：**
```
┌─────────────────────────────────────────────────────────────────┐
│                     对账流程（校准版）                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  日报数据              平台数据              对账结果            │
│  ┌──────┐            ┌──────┐            ┌──────────┐         │
│  │消耗:X│            │消耗:Y│     →      │ 待对账   │         │
│  │进粉:N│            │手续费:F│           │ 差异:X-Y │         │
│  └──────┘            └──────┘            └────┬─────┘         │
│                                               │                │
│                                     ┌─────────↓─────────┐      │
│                                     │   人工裁决        │      │
│                                     ├───────────────────┤      │
│                                     │ ○ 以日报为准      │      │
│                                     │ ○ 以平台为准      │      │
│                                     │ ○ 人工填写        │      │
│                                     │ ○ 待核实          │      │
│                                     └───────────────────┘      │
│                                               ↓                │
│                                     reconcile_status = 已确认  │
│                                     reconciled_value = ?       │
│                                     reconciled_by = 操作人     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

---

### 4.4 月度结算流程校准

| 原流程 | 校准后 |
|--------|--------|
| 月初 1-3日 | → 删除固定时间，引入"结算期(settlement_period)" |
| 自动汇总 | → 系统汇总后，需人工确认 |
| 计算毛利 | → 展示计算值，增加"毛利确认状态" |
| 输出报表 | → 仅"已确认"状态的数据可出报表 |

**校准后流程：**
```
创建结算期 ──→ 系统自动汇总 ──→ 人工复核 ──→ 确认锁定
(人工)         (草稿状态)      (待确认)     (已锁定)
                  ↓               ↓            ↓
              可修改           可修改       不可修改
                                             (特殊解锁需审批)
```

**新增字段：**
- `settlement_period`: 结算期标识（如 "2025-11"）
- `settlement_status`: 草稿 / 待确认 / 已锁定
- `locked_by`, `locked_at`: 锁定操作人和时间

---

### 4.5 KPI 计算校准

| 原流程 | 校准后 |
|--------|--------|
| 自动计算 CPL | → 展示计算值，标记数据来源 |
| 直接用于考核 | → 仅作为"参考视图"，不作为系统规则 |

**校准后逻辑：**
```
KPI 视图（仅供参考，不参与业务规则）
├── 数据来源标记：日报 / 平台 / 人工确认
├── 空值处理：进粉数=0 时，CPL 显示"N/A"而非报错
└── 警示标记：差异超过 20% 时，标记"数据待核实"
```

## 五、MVP 阶段必须显式保留的"人工裁决点"

### 裁决点清单

| # | 裁决点 | 触发条件 | 系统行为 | 人工动作 | 必要字段 |
|---|--------|----------|----------|----------|----------|
| 1 | **消耗差异裁决** | 日报消耗 ≠ 平台消耗 | 展示差异值 | 选择采信来源 | `reconcile_status`, `reconciled_value`, `reconciled_by` |
| 2 | **手续费确认** | fee 为空 或 fee ≠ 计算值 | 展示原值/计算值 | 确认最终值 | `fee_confirmed`, `fee_source` |
| 3 | **收入确认** | 录入客户付款 | 展示待确认列表 | 确认归属项目和周期 | `revenue_status`, `confirmed_by` |
| 4 | **项目归属** | 消耗记录需归属 | 基于规则建议 | 确认或修改 | `project_id`, `project_assigned_by` |
| 5 | **预付款分摊** | 预付款需分配 | 仅记录总额 | 手动创建分摊 | `allocation_records` (独立表) |
| 6 | **结算锁定** | 月度结算完成 | 展示待锁定列表 | 确认锁定 | `settlement_status`, `locked_by` |

### 裁决点状态机

```
                 ┌─────────────────────────────────────┐
                 │         裁决点通用状态机             │
                 ├─────────────────────────────────────┤
                 │                                     │
                 │   ┌────────┐    人工操作   ┌────────┐
                 │   │ 待处理 │ ──────────→  │ 已确认 │
                 │   │PENDING │              │CONFIRMED│
                 │   └────┬───┘              └────┬───┘
                 │        │                       │
                 │        │ 标记争议              │ 发现问题
                 │        ↓                       ↓
                 │   ┌────────┐              ┌────────┐
                 │   │ 争议中 │ ←─────────── │ 已撤回 │
                 │   │DISPUTED│   重新提交   │REVOKED │
                 │   └────────┘              └────────┘
                 │                                     │
                 └─────────────────────────────────────┘
```

## 六、下一步在系统设计中需要额外补充说明的事项

### 6.1 数据质量边界（必须定义）

| 事项 | 需要明确 |
|------|----------|
| 空值处理 | 哪些字段允许为空？空值在计算中如何处理？ |
| 错误数据标记 | 如何标记"疑似错误"数据？是否允许修改历史数据？ |
| 数据溯源 | 每条记录是否需要保留"数据来源"和"录入时间"？ |

### 6.2 时间边界（必须定义）

| 事项 | 需要明确 |
|------|----------|
| 补录期限 | 日报最多可以补录多少天前的数据？ |
| 调整期限 | 结算锁定后，调整最多可以追溯多久？ |
| 数据有效期 | 多久之前的数据可以归档不再修改？ |

### 6.3 权限边界（必须定义）

| 事项 | 需要明确 |
|------|----------|
| 裁决权限 | 谁可以做对账裁决？谁可以覆盖系统值？ |
| 锁定权限 | 谁可以锁定结算？锁定后谁可以解锁？ |
| 数据修改 | 历史数据的修改需要什么审批流程？ |

### 6.4 状态机定义（必须补充）

需要为以下实体定义完整状态机：
- 日报记录 (daily_report)
- 消耗记录 (ad_spend_daily)
- 对账记录 (reconciliation)
- 结算期 (settlement_period)
- 项目 (project)

### 6.5 异常处理（必须定义）

| 异常场景 | 需要明确处理方式 |
|----------|------------------|
| 对账差异超过 X% | 是否自动告警？是否阻止结算？ |
| 预付款不足 | 是否允许继续投放？如何预警？ |
| 账户被封 | 如何标记？历史数据如何处理？ |
| 投手离职 | 数据归属如何处理？ |

### 6.6 历史数据处理（必须定义）

| 事项 | 需要明确 |
|------|----------|
| 2024年数据 | 是否迁移？如何标记为"历史归档"？ |
| 存量预付款 | 如何初始化余额？从哪个时点开始追踪？ |
| 存量项目 | 如何补录项目信息？是否需要规范化命名？ |

## 总结

**这份流程文档的定位：**
- ✓ 可作为【业务认知稿】，帮助新人理解业务全貌
- ✗ 不可直接作为【系统设计依据】，需要加入本校准报告的约束

**MVP 阶段核心原则：**

```
┌──────────────────────────────────────────────────────────────────┐
│                     MVP 系统设计原则                              │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. 记录优先于判断                                                │
│     → 系统先完整记录原始数据，再做分析                            │
│                                                                  │
│  2. 展示优先于计算                                                │
│     → 系统展示多个来源，不自动得出结论                            │
│                                                                  │
│  3. 人工确认优先于自动规则                                        │
│     → 关键节点必须人工确认，不做自动化                            │
│                                                                  │
│  4. 允许脏数据存在，但必须标记                                    │
│     → 不拒绝录入，但标记"待核实""数据异常"                       │
│                                                                  │
│  5. 先能用，再规范                                                │
│     → MVP 先跑起来，逐步约束数据质量                              │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```
