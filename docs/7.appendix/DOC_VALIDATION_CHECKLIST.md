## 📌 文档说明

本检查清单适用于 **所有 SoT 文档、开发指南、业务流程文档** 的创建与审查。

**使用场景**:
1. **文档创建**: 新建文档前，按清单确保完整性
2. **文档审查**: PR 审查时，使用清单验证文档质量

4. **AI 辅助开发**: Claude/SuperClaude 生成文档时，必须通过本清单验证

**检查流程**:
```
创建文档 → 自检（Tier 1-6）→ 同行审查 → 架构审查 → 合并
```

## Tier 1: 文档元信息

**目的**: 确保文档有清晰的版本、状态、维护责任

### 1.1 必填字段

```markdown
> **文档版本**: vX.Y
> **发布日期**: YYYY-MM-DD
> **文档状态**: ✅ Active / 🟡 Draft / ❌ Deprecated
> **维护团队**: XXX Team
> **最后审查**: YYYY-MM-DD
> **文档定位**: 一句话说明文档用途
```

**检查项**:
- [ ] 文档包含完整的元信息块（6 个字段）
- [ ] 文档版本遵循语义化版本号（v1.0, v2.1）
- [ ] 文档状态清晰标注（Active / Draft / Deprecated）
- [ ] 维护团队明确（非"待定"或空白）
- [ ] 最后审查日期在 3 个月内（Active 文档）
- [ ] 文档定位不超过 100 字

---

### 1.2 变更历史

**检查项**:
- [ ] 文档包含"变更历史"章节
- [ ] 变更历史记录最近 3 次主要变更
- [ ] 每次变更包含：版本号、日期、变更内容
- [ ] 变更内容使用 ✅/❌/🔄 符号标注类型

**示例**:
```markdown
## 变更历史

### v2.1 (2025-11-20)
- ✅ 新增趋势风控规则 TF-003
- 🔄 修订 8 状态机流转图
- ❌ 删除已废弃的 4 状态机

### v2.0 (2025-10-15)
- ✅ 重构状态机章节
```

## Tier 2: SoT 一致性

**目的**: 确保文档内容与上游 SoT 文档一致

### 2.1 引用 SoT 规范

**检查项**:
- [ ] 涉及数据库字段时，明确引用 `DATA_SCHEMA.md` 版本号和章节
- [ ] 涉及状态流转时，明确引用 `STATE_MACHINE.md` 版本号和章节
- [ ] 涉及业务规则时，明确引用 `BUSINESS_RULES.md` 规则编号
- [ ] 涉及错误码时，明确引用 `ERROR_CODES_SOT.md` 错误码
- [ ] 涉及 API 端点时，明确引用 `API_SOT.md` 版本号和章节

**示例**:
```markdown
**引用**: DATA_SCHEMA.md v5.2 §3.3.1 - daily_reports 表
**引用**: STATE_MACHINE.md v2.6 §8 - 粉数确认状态机
**引用**: BUSINESS_RULES.md v4.1 - BR-RPT-005
**引用**: ERROR_CODES_SOT.md v2.1 - STATE_400
```

---

### 2.2 禁止重复定义

**检查项**:
- [ ] 文档不重复定义状态枚举（必须引用 `STATE_MACHINE.md`）
- [ ] 文档不重复定义错误码（必须引用 `ERROR_CODES_SOT.md`）
- [ ] 文档不重复定义表结构（必须引用 `DATA_SCHEMA.md`）
- [ ] 文档不重复定义角色枚举（必须引用 `BUSINESS_RULES.md`）

**反例**:
```markdown
❌ 错误：重复定义状态
日报状态包括：draft, pending, approved, rejected

✅ 正确：引用 SoT
日报状态遵循 STATE_MACHINE.md v2.6 §8 定义的 8 状态机：
raw_submitted → trend_pending → ... → final_locked
```

---

### 2.3 裁判链一致性

**检查项**:
- [ ] 文档明确标注在裁判链中的位置
- [ ] 文档引用的上游 SoT 版本号正确
- [ ] 文档内容不与上游 SoT 冲突

**裁判链**:
```
MASTER.md → STATE_MACHINE.md → DATA_SCHEMA.md → BUSINESS_RULES.md
→ API_SOT.md → ERROR_CODES_SOT.md → AUTH_SPEC.md → LEDGER_SOT.md
```

**检查方法**:
- [ ] 如果文档是 SoT，标注其在裁判链中的优先级
- [ ] 如果文档不是 SoT，标注其依赖的 SoT 文档

## Tier 4: 可执行性

**目的**: 确保开发者仅凭此文档即可完成开发任务

### 4.1 完整性检查

**检查项**:
- [ ] 文档包含"使用指南"或"快速开始"章节
- [ ] 文档包含完整的示例代码（Python / TypeScript / SQL）
- [ ] 示例代码可直接复制运行（无占位符 `...` 或 `TODO`）
- [ ] 文档包含错误处理示例

**示例**:
```python
# ✅ 正确：完整示例
from backend.services.daily_report_service import DailyReportService
from backend.schemas.daily_report import DailyReportCreate
from decimal import Decimal

data = DailyReportCreate(
    ad_account_id=123,
    report_date="2025-11-26",
    conversions_raw=100,
    raw_spend=Decimal('500.00')
)
service = DailyReportService(db)
result = service.submit_raw_report(data, current_user_id)

# ❌ 错误：不完整示例
service.submit_raw_report(...)  # 缺少参数定义
```

---

### 4.2 决策树 / 流程图

**检查项**:
- [ ] 复杂流程包含决策树或流程图
- [ ] 流程图使用 Mermaid 或 ASCII 艺术格式
- [ ] 流程图包含分支条件和终态

**示例**:
```
收到充值申请 → 检查申请人角色
   ↓
   ├─ media_buyer/account_manager → 提交申请
   └─ 其他角色 → 返回 AUTH_500
   ↓
data_operator 复核 → 检查金额合规性
   ↓
   ├─ 合规 → 流转至 finance_approve
   └─ 不合规 → 拒绝
```

---

### 4.3 错误处理

**检查项**:
- [ ] 文档包含常见错误场景及处理方法
- [ ] 错误码与 `ERROR_CODES_SOT.md` 一致
- [ ] 包含错误排查步骤

**示例**:
```markdown
### 常见错误

**错误码 `STATE_400`: 非法状态流转**
- **场景**: 尝试从 `final_locked` 回退至 `draft`

- **解决**: 使用 REVERSAL 红冲机制修正数据
```

## 使用建议

### 对于文档作者

1. **创建阶段**: 按 Tier 1 → Tier 6 顺序自检
2. **提交 PR**: 在 PR 描述中附上检查清单，标注已通过的项
3. **审查反馈**: 根据审查意见，更新文档并重新自检

---

### 对于 Code Reviewer

1. **基础检查**: 优先检查 Tier 1（元信息）和 Tier 2（SoT 一致性）
2. **深度检查**: 根据文档类型，执行专项检查（SoT / DEV / API）
3. **一致性验证**: 使用脚本工具验证引用的 SoT 版本号

---

### 对于 AI 工具 (Claude/SuperClaude)

1. **生成文档后**: 立即运行本检查清单自检
2. **输出格式**: 在响应中附上检查清单，标注通过/失败项
3. **失败项修正**: 自动修正失败项，或向用户说明原因
