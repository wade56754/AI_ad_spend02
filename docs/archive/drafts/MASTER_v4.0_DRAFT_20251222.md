## 第一章：系统定位

### 1.1 业务场景

本系统管理 Facebook/TikTok 广告投放的日消耗数据，核心业务流程：

```
Excel消耗汇总表 → 系统导入 → 投手确认 → 主管审核 → 财务核算 → 对账结算
```

**真实业务数据规模**（以12月消耗汇总-ZZ.xlsx为例）：
- 数据量：396 行/月
- 投手：8 人（HY、LD、LM、YJ、YK、JK、HW 等）
- 平台：FB（197条）、TK（5条）
- 月消耗：约 13,627.56 美元

### 1.2 管理者核心诉求

| 维度 | 管理者关心什么 | 系统解决什么 |
|------|---------------|-------------|
| **人** | 投手怎么管理？角色怎么分？ | 投手日报填报、绩效统计、权限隔离 |
| **事** | 项目如何推进？流程如何简化？ | 项目管理、账户分配、审核流程 |
| **钱** | 资金如何流动？如何对账？ | 消耗统计、手续费计算、财务对账 |
| **数据** | 数据如何产生？如何校准？ | Excel导入、趋势校验、数据确认 |

### 1.3 四个核心模块

```
┌─────────────────────────────────────────────────────────────┐
│                    AI 广告代投系统                           │
├─────────────────┬─────────────────┬─────────────────────────┤
│   投手管理模块   │   项目管理模块   │   广告账号管理模块       │
│   (日报/绩效)   │   (项目/分配)   │   (账户/代理商)         │
├─────────────────┴─────────────────┴─────────────────────────┤
│                    财务管理模块                              │
│              (消耗统计/手续费/对账/结算)                     │
└─────────────────────────────────────────────────────────────┘
```

### 1.4 系统演进路径

| 阶段 | 目标 | 核心能力 | 完成标志 |
|------|------|---------|---------|
| **MVP** | 能用 | Excel导入 → 日报管理 → 消耗统计 | 投手可以查看/确认日报 |
| **Phase 1** | 可对账 | 趋势校验 → 审核流程 → 自动对账 | 财务可以完成月度对账 |
| **Phase 2** | 可审计 | 审计不可逆 → 双账本 → 红冲机制 | 通过外部审计 |

## 第二章：原始数据结构

### 2.1 Excel消耗汇总表字段映射

本章定义 Excel 原始数据与系统字段的映射关系，是数据导入的唯一依据。

| # | Excel列名 | 系统表.字段 | 数据类型 | 说明 |
|---|-----------|------------|---------|------|
| 1 | 日期 | `daily_reports.report_date` | DATE | 投放日期 |
| 2 | 地区 | `daily_reports.region` | VARCHAR | 印度/新加坡等 |
| 3 | 投手 | `users.pitcher_code` | VARCHAR | HY/LD/LM/YJ/YK/JK/HW |
| 4 | 账户名称/ID | `ad_accounts.account_name` | VARCHAR | 广告账户标识 |
| 5 | 账户种类 | `ad_accounts.account_type` | ENUM | 越南盾主题户/美金户 |
| 6 | 代理商 | `suppliers.name` | VARCHAR | 海总&志诚三不限 等 |
| 7 | 平台 | `ad_accounts.platform` | ENUM | FB/TK |
| 8 | 转点截图Today MAX | `daily_reports.conversions_raw` | DECIMAL | 投手填报的粉数 |
| 9 | 转点截图yesterday MAX | `daily_reports.conversions_prev` | DECIMAL | 昨日粉数（趋势校验用） |
| 10 | 备注 | `daily_reports.notes` | TEXT | 备注信息 |
| 11 | 手续费 | `daily_reports.service_fee` | DECIMAL | 服务费（按费率计算） |
| 12 | 实际消耗 | `daily_reports.raw_spend` | DECIMAL | 真实广告花费 |
| 13 | 包含手续费的消耗 | `daily_reports.total_spend` | DECIMAL | 实际消耗 + 手续费 |

### 2.2 数据样例

```
日期: 2025-12-01
地区: 印度
投手: HY
账户名称/ID: SONZDD-ADA+7-GX-324 (1138647123633445)
账户种类: 越南盾主题户
代理商: 海总&志诚三不限
平台: FB
转点截图Today MAX: 13.54548（粉数）
手续费: 1.354548
实际消耗: 13.54548
包含手续费的消耗: 14.900028
```

### 2.3 唯一键约束

日报的唯一键 = `(report_date, pitcher_code, account_id)`

即：同一天、同一投手、同一账户只能有一条日报记录。

## 第三章：四个核心模块

### 3.1 投手管理模块

**模块职责**：管理投手的日报填报、绩效统计

**数据表**：
- `users`：投手基本信息（pitcher_code: HY/LD/LM/YJ/YK/JK/HW）
- `daily_reports`：日报数据

**MVP功能**：
| 功能 | 描述 | 操作权限 |
|------|------|---------|
| 查看日报列表 | 投手查看自己的日报 | 投手本人 |
| 编辑日报 | 补充/修改日报数据 | 投手本人（未提交前） |
| 提交日报 | 确认日报数据 | 投手本人 |
| 绩效统计 | 按日/周/月统计消耗和粉数 | 投手本人 |

**模块边界（不可变）**：
```yaml
可写表:
  - daily_reports（仅自己的，仅未提交状态）
  - users（仅自己的基本信息）
只读表:
  - ad_accounts
  - projects
  - suppliers
禁止表:
  - ledger_entries
  - reconciliation_*
  - 其他投手的 daily_reports
```

**不变量**：
- INV-P1：投手只能操作自己的日报
- INV-P2：已提交的日报投手不能修改（需主管退回）
- INV-P3：日报唯一键 = (report_date, pitcher_code, account_id)

### 3.3 广告账号管理模块

**模块职责**：管理广告账户、代理商、归属关系

**数据表**：
- `ad_accounts`：广告账户
- `suppliers`：代理商/供应商
- `account_ownership_history`：账户归属历史

**MVP功能**：
| 功能 | 描述 | 操作权限 |
|------|------|---------|

| 状态管理 | active/suspended/dead | 户管/管理员 |
| 归属分配 | 将账户分配给投手 | 户管/管理员 |
| 代理商管理 | 管理供应商信息 | 财务/管理员 |

**账户状态（MVP简化）**：
```python
AD_ACCOUNT_STATUS = frozenset(['active', 'suspended', 'dead'])
```

**模块边界（不可变）**：
```yaml
可写表:
  - ad_accounts
  - suppliers
  - account_ownership_history
只读表:
  - users
  - projects
禁止表:
  - ledger_entries
  - daily_reports（写）
```

**不变量**：
- INV-A1：同一账户同一时间只能归属一个投手
- INV-A2：dead状态账户不可恢复为active

### 3.4 财务管理模块

**模块职责**：消耗统计、手续费计算、对账结算

**数据表**：
- `ledger_entries`：账本流水
- `reconciliation_batches`：对账批次
- `reconciliation_details`：对账明细

**MVP功能**：
| 功能 | 描述 | 操作权限 |
|------|------|---------|
| 消耗统计 | 按投手/地区/平台/代理商统计 | 财务/主管 |
| 手续费计算 | 按费率计算服务费 | 系统自动 |
| 导出报表 | 导出消耗汇总报表 | 财务/管理员 |

**Phase 1 功能**：
- 自动对账：系统消耗 vs Excel导入消耗
- 差异标记：标记差异超过阈值的记录

**Phase 2 功能**：
- 双账本分离：PROJECT账本（收入侧）/ SUPPLIER账本（成本侧）
- 账本不可逆：禁止UPDATE/DELETE，只能红冲
- 期间锁：锁定已对账期间

**模块边界（不可变）**：
```yaml
可写表:
  - ledger_entries（MVP允许UPDATE，Phase 2仅INSERT）
  - reconciliation_batches
  - reconciliation_details
只读表:
  - daily_reports
  - ad_accounts
  - suppliers
禁止表:
  - users（修改）
  - projects（修改）
```

**不变量**：
- INV-F1：余额 = SUM(ledger_entries.amount)
- INV-F2：手续费 = 实际消耗 × 费率
- INV-F3：总消耗 = 实际消耗 + 手续费

## 第四章：状态机（分阶段启用）

### 4.1 MVP阶段：简化状态机

```
┌─────────┐    投手提交    ┌───────────┐    主管确认    ┌───────────┐
│  draft  │ ────────────> │ submitted │ ────────────> │ confirmed │
└─────────┘               └───────────┘               └───────────┘
     │                          │                           
     │        主管退回           │                           
     └──────────────────────────┘                           
```

**状态定义**：
| 状态 | 说明 | 可操作角色 |
|------|------|----------|
| draft | 草稿（Excel导入后/投手创建） | 投手 |
| submitted | 已提交（投手确认后） | 主管 |
| confirmed | 已确认（主管审核后） | 财务（只读） |

**状态白名单（MVP）**：
```python
MVP_REPORT_STATUS = frozenset(['draft', 'submitted', 'confirmed'])
```

### 4.2 Phase 1：完整状态机

```
                              ┌──────────────┐
                              │ trend_flagged│
                              └──────┬───────┘
                                     │ 人工审核
                                     ▼
┌──────────────┐  系统   ┌───────────────┐   ┌─────────────────┐
│ raw_submitted│ ──────> │ trend_pending │ ─>│ trend_resolved  │
└──────────────┘         └───────┬───────┘   └────────┬────────┘
                                 │ 趋势正常           │
                                 ▼                   ▼
                         ┌───────────┐       ┌───────────────┐
                         │ trend_ok  │ ─────>│ final_pending │
                         └───────────┘       └───────┬───────┘
                                                     │ 运营确认
                                                     ▼
                                             ┌─────────────────┐
                                             │ final_confirmed │
                                             └─────────────────┘
```

**状态白名单（Phase 1）**：
```python
PHASE1_REPORT_STATUS = frozenset([
    'raw_submitted', 'trend_pending', 'trend_ok', 
    'trend_flagged', 'trend_resolved', 
    'final_pending', 'final_confirmed'
])
```

### 4.3 Phase 2：审计级状态机

在 Phase 1 基础上增加：
- `final_locked`：终态，数据冻结，触发计费/计成本

**终态保护**：
- final_locked 后禁止修改任何字段
- 错误修正只能通过红冲（REVERSAL）

## 第七章：AI 编码治理

### 7.1 状态值白名单

AI 生成代码时，状态值必须来自以下白名单：

```python
# ===== MVP阶段 =====
MVP_REPORT_STATUS = frozenset(['draft', 'submitted', 'confirmed'])
MVP_ACCOUNT_STATUS = frozenset(['active', 'suspended', 'dead'])
MVP_PROJECT_STATUS = frozenset(['active', 'archived'])

# ===== Phase 1 =====
PHASE1_REPORT_STATUS = frozenset([
    'raw_submitted', 'trend_pending', 'trend_ok', 
    'trend_flagged', 'trend_resolved', 
    'final_pending', 'final_confirmed'
])

# ===== Phase 2 =====
PHASE2_REPORT_STATUS = PHASE1_REPORT_STATUS | {'final_locked'}

# ===== 通用 =====
USER_ROLE = frozenset(['pitcher', 'supervisor', 'finance', 'account_manager', 'admin', 'ceo'])
PLATFORM = frozenset(['FB', 'TK'])
```

### 7.2 模块边界检查

AI 在生成代码前必须完成以下检查：

```
□ 步骤1：确定任务属于哪个模块
  - 投手管理：涉及日报填报、投手信息
  - 项目管理：涉及项目、客户、成员
  - 广告账号管理：涉及账户、代理商、归属
  - 财务管理：涉及流水、对账、统计

□ 步骤2：检查目标表是否在可写范围内
  - 参考第三章各模块的"模块边界"定义

□ 步骤3：检查状态值是否在白名单内
  - 参考第七章7.1状态值白名单

□ 步骤4：检查是否跨模块写入
  - 禁止投手管理写ledger
  - 禁止财务管理写daily_reports
```

### 7.3 AI 必须停止的场景

| 场景 | 处理方式 |
|------|---------|
| Excel列不在第二章映射表中 | 停止 → 标注缺失 → 询问用户 |
| 状态值不在白名单内 | 停止 → 查阅 STATE_MACHINE.md |
| 跨模块写入 | 停止 → 拒绝执行 |
| SoT 文档冲突 | 停止 → 引用裁判链 → 询问用户 |
| 发明新字段/新状态/新角色 | 停止 → 拒绝执行 |

### 7.4 禁止行为清单

| 编号 | 禁止行为 | 原因 |
|------|---------|------|
| ZT-01 | 发明新状态值 | 状态机失效 |
| ZT-02 | 发明新角色 | 权限混乱 |
| ZT-03 | 跨模块写入 | 模块边界破坏 |
| ZT-04 | UPDATE/DELETE ledger（Phase 2） | 账本不可信 |
| ZT-05 | 绕过状态机直接修改status | 流程断裂 |
| ZT-06 | 硬编码状态/角色枚举 | 必须引用白名单 |
