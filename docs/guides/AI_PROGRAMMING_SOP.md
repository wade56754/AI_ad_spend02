## 第二章：新手的"最小可运行版本(MVP)"定义

### 2.1 MVP 范围矩阵

| 功能 | Phase 1 必做 | Phase 2 可选 | 原因 |
|------|-------------|-------------|------|
| **登录认证** | ✅ JWT 登录 | OAuth | 最小可用 |
| **角色权限** | ✅ 6角色固定权限 | 动态权限 | 业务清晰 |
| **日报提交** | ✅ 3状态简化版 | 8状态完整版 | 先跑通流程 |
| **充值审批** | ✅ 单级审批 | 多级审批 | 业务够用 |
| **账本记账** | ✅ 项目账本 | 供应商账本 | 核心账本优先 |
| **利润报表** | ✅ 项目利润 | 多维分析 | 老板刚需 |
| **对账流程** | ⚠️ 手动触发 | 自动对账 | 复杂度高，后做 |
| **异常告警** | ❌ 不做 | 后续迭代 | 非 MVP |

### 2.2 MVP 的"不做清单"（同样重要）

| 不做的事 | 为什么不做 | 什么时候做 |
|----------|-----------|-----------|
| 自动阻断/拒绝 | Phase 1 只记录不阻断 | Phase 2 |
| 复杂权限继承 | 增加复杂度 | 业务需要时 |
| 国际化 | 先做中文 | 有海外需求时 |
| 移动端适配 | 桌面优先 | 用户反馈后 |
| 数据大屏 | 非核心 | 报表稳定后 |

### 2.3 MVP 验收标准（必须全部通过）

```yaml
MVP_验收清单:
  用户故事:
    - [ ] 投手能登录系统
    - [ ] 投手能提交日报（消耗+粉数）
    - [ ] 运营能审核日报并确认粉数
    - [ ] 财务能发起充值申请
    - [ ] 老板能审批充值
    - [ ] 老板能看到项目利润

  技术验收:
    - [ ] 所有接口有权限校验
    - [ ] 金额字段使用 Decimal(15,2)
    - [ ] 关键操作有审计日志
    - [ ] 数据库迁移可回滚
    - [ ] 测试覆盖率 > 60%
```

```
│    │PRD/SoT│ ──────→ │ 精确  │ ───────→ │ 代码  │             │
│    │ 文档  │         │ 提示词│          │ 生成  │             │
│    └───────┘         └───────┘          └───┬───┘             │
│                                              │                  │
│    ⑥ PR门禁          ⑤ 修复循环         ④ 测试验证             │
│    ┌───────┐         ┌───────┐          ┌───┴───┐             │
│    │ 合并  │ ←────── │ 修改  │ ←──────  │ 运行  │             │
```

### 3.2 每一步的具体操作

#### 步骤 ①：拆任务

| 动作 | 命令/操作 | 验证方式 |
|------|----------|----------|
| 读 PRD 找到功能点 | 打开 PRD 文档 | 能用一句话描述这个功能 |
| 查 SoT 找约束 | 读 BUSINESS_RULES.md | 找到对应的 BR-XXX 规则 |
| 写任务卡 | 用模板填写 | 任务卡包含：输入/输出/约束/测试点 |

**任务卡模板**：
```markdown
## 任务：[功能名称]

### 输入
- 用户操作：[用户做什么]
- 请求数据：[请求体字段]

### 输出
- 成功响应：[返回什么]
- 错误响应：[可能的错误]

### 约束（从 SoT 抄）
- BR-XXX-001: [规则描述]
- 状态机：[允许的状态转换]

### 测试点
- [ ] 正常路径
- [ ] 权限校验
- [ ] 边界条件
```

#### 步骤 ②：写提示词

**黄金公式**：
```
提示词 = 背景 + 任务 + 约束 + 示例 + 验收标准
```

**示例提示词**（给 Claude Code）：
```markdown
## 背景
我在开发 AI 广告代投系统的日报提交功能。

## 任务
实现 POST /api/daily-reports 接口，让投手提交日报。

## 约束（必须遵守）
1. 参考 BR-RPT.md 的规则
2. 只有 pitcher 角色可以提交
3. 金额使用 Decimal(15,2)
4. 状态固定为 raw_submitted
5. 必须记录 created_by 和 created_at

## 示例
请求体：
{
  "ad_account_id": 1,
  "report_date": "2025-01-15",
  "raw_spend": "1234.56",
  "conversions_raw": 100
}

## 验收标准
- [ ] 接口能正常返回
- [ ] 非 pitcher 返回 403
- [ ] 缺少必填字段返回 400
- [ ] 写测试覆盖以上场景
```

#### 步骤 ③：AI 生成代码

| 动作 | 说明 |
|------|------|
| 发送提示词 | 把上面的提示词发给 Claude Code |
| 等待生成 | AI 会生成代码文件 |
| **不要**立即接受 | 先阅读，确认符合约束 |

#### 步骤 ④：测试验证

**必须运行的命令**：
```bash
# 1. 运行单元测试
pytest tests/ -v

# 2. 运行代码检查
ruff check .

# 3. 运行类型检查
mypy backend/

# 4. 查看测试覆盖率
pytest --cov=backend tests/
```

**验证标准**：
| 检查项 | 通过标准 | 不通过怎么办 |
|--------|----------|-------------|
| 测试结果 | 0 failed | 让 AI 修复失败的测试 |
| 代码检查 | 0 errors | 让 AI 修复 lint 错误 |
| 类型检查 | 0 errors | 让 AI 添加类型注解 |
| 覆盖率 | > 60% | 让 AI 补充测试用例 |

#### 步骤 ⑤：修复循环

**修复提示词模板**：
```markdown
测试失败了，请修复：

## 错误信息
[粘贴测试输出]

## 要求
1. 不要改测试，改代码
2. 修复后重新运行测试确认
3. 解释修复了什么
```

#### 步骤 ⑥：PR 门禁

**提交前检查清单**：
```bash
# 1. 确保所有测试通过
pytest tests/ -v

# 2. 确保代码检查通过
ruff check .

# 3. 查看要提交的文件
git status

# 4. 添加文件
git add [文件路径]

# 5. 提交（使用规范格式）
git commit -m "feat(daily-report): 实现日报提交接口"

# 6. 推送

```

## 第四章：需求拆分方法

### 4.1 拆分原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **单一职责** | 一个任务只做一件事 | ❌ "实现日报功能" → ✅ "实现日报提交接口" |
| **可测试** | 必须能写测试验证 | ❌ "优化用户体验" → ✅ "提交成功显示成功提示" |
| **可演示** | 完成后能看到效果 | ❌ "重构代码" → ✅ "重构后测试全部通过" |
| **2小时原则** | 一个任务不超过2小时 | 超过就继续拆分 |

### 4.2 拆分模板

**从 SoT 到任务的拆分流程**：

```
BUSINESS_RULES.md (BR-RPT)
    │
    ├── BR-RPT-001: 日报提交人
    │   └── 任务1: 实现角色校验中间件

    ├── BR-RPT-004: 状态流转合法性
```

## 第五章：SoT 驱动开发法

### 5.1 SoT 文档体系

| 文档 | 职责 | 开发时查询场景 |
|------|------|---------------|
| **MASTER.md** | 架构宪法、角色定义、防幻觉原则 | 确认角色权限、Phase 约束 |
| **STATE_MACHINE.md** | 状态枚举、合法流转 | 写状态变更代码时 |
| **DATA_SCHEMA.md** | 表结构、字段类型 | 写数据库迁移时 |
| **BUSINESS_RULES.md** | 业务规则索引 | 确认业务约束 |
| **BR-*.md** | 规则详细定义 | 写具体功能时 |
| **ERROR_CODES.md** | 错误码定义 | 处理错误响应时 |
| **AUTH_SPEC.md** | 权限规范 | 写权限校验时 |

### 5.2 SoT 查询流程

```
开发任务 ──→ 查 BUSINESS_RULES.md 找规则ID
              │
              ├── 查 BR-*.md 找详细约束
              │
              ├── 查 STATE_MACHINE.md 找状态流转
              │
              ├── 查 DATA_SCHEMA.md 找字段定义
              │
              └── 查 ERROR_CODES.md 找错误码
```

### 5.3 SoT 约束检查清单

**每写一个功能，必须回答以下问题**：

| 检查项 | 查哪个文档 | 填写内容 |
|--------|-----------|----------|
| 谁能执行这个操作？ | AUTH_SPEC.md | 角色：_______ |
| 涉及哪些状态变更？ | STATE_MACHINE.md | 从___到___ |
| 涉及哪些数据表？ | DATA_SCHEMA.md | 表：_______ |
| 有哪些业务规则？ | BR-*.md | 规则：BR-___-___ |
| 失败返回什么错误码？ | ERROR_CODES.md | 错误码：_______ |

### 5.4 SoT 违反检测

**代码审查时必查的 SoT 违规**：

| 违规类型 | 如何检测 | 严重程度 |
|----------|---------|----------|
| 状态直接 UPDATE | 搜索 `UPDATE.*status` | 🔴 严重 |
| 金额用 float | 搜索 `float.*amount\|spend` | 🔴 严重 |
| 缺少权限校验 | 接口无 `@require_role` | 🟡 警告 |
| 硬编码角色名 | 搜索 `"admin"\|"pitcher"` | 🟡 警告 |
| 缺少审计日志 | 关键操作无日志记录 | 🟡 警告 |

## 第七章：财务/账本模块的"高风险清单"

### 7.1 财务模块风险矩阵

| 风险项 | 风险等级 | 后果 | 防护措施 |
|--------|---------|------|---------|
| 金额精度丢失 | 🔴 致命 | 账目对不上 | 强制 Decimal(15,2) |
| 账本数据被改 | 🔴 致命 | 无法审计 | 禁止 UPDATE/DELETE |
| 双账本不一致 | 🔴 致命 | 资金混乱 | 事务一致性 |

| 缺少审计日志 | 🟠 严重 | 无法追溯 | 强制审计记录 |
| 终态被修改 | 🟠 严重 | 数据篡改 | 终态保护 |

### 7.2 财务开发铁律（必须遵守）

```

│                                                                 │
│  铁律 6: 终态（locked/completed）不可逆转                        │
│                                                                 │

│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 7.3 双账本一致性检查

**账本公式**：
```
项目可用余额 = 期初余额 + Σ充值 - Σ消耗
供应商应付余额 = Σ消耗 - Σ已付款
```

**一致性校验 SQL**：
```sql
-- 每日运行，检查账本平衡
SELECT
  project_id,
  SUM(CASE WHEN entry_type = 'TOPUP' THEN amount ELSE 0 END) as total_topup,
  SUM(CASE WHEN entry_type = 'SPEND' THEN amount ELSE 0 END) as total_spend,
  SUM(CASE WHEN entry_type = 'REVENUE' THEN amount ELSE 0 END) as total_revenue
FROM ledger_entries
GROUP BY project_id
HAVING SUM(amount) != 0; -- 不平衡的记录
```

### 7.4 幂等性实现

**错误示范** ❌：
```python
# 没有幂等检查，重复请求会重复记账
def create_topup(amount):
    ledger.insert(amount=amount)
```

**正确示范** ✅：
```python
# 使用幂等键防止重复
def create_topup(amount, idempotency_key):
    # 检查是否已处理
    existing = ledger.query(idempotency_key=idempotency_key)
    if existing:
        return existing  # 返回已有记录，不重复创建

    # 首次处理
    return ledger.insert(
        amount=amount,
        idempotency_key=idempotency_key
    )
```

### 8.2 每个错误的解决策略

#### 错误 #1：金额用 float

| 项目 | 内容 |
|------|------|
| **错误示范** | `amount: float = 0.0` |
| **正确做法** | `amount: Decimal = Decimal("0.00")` |
| **检测方法** | `grep -r "float.*amount\|spend\|price"` |
| **预防措施** | 在 SoT 中强调，代码审查必查 |

#### 错误 #2：忘记写测试

| 项目 | 内容 |
|------|------|
| **表现** | 新功能没有对应的测试文件 |
| **正确做法** | 每个功能必须有测试 |
| **检测方法** | `pytest --cov` 覆盖率 < 60% 报警 |
| **预防措施** | PR 门禁强制覆盖率检查 |

#### 错误 #3：硬编码敏感信息

| 项目 | 内容 |
|------|------|
| **错误示范** | `password = "admin123"` |
| **正确做法** | `password = os.getenv("DB_PASSWORD")` |
| **检测方法** | 使用 git-secrets 或 ruff 规则 |
| **预防措施** | `.env.example` 只放键名不放值 |

#### 错误 #4：忘记权限校验

| 项目 | 内容 |
|------|------|
| **表现** | 接口任何人都能调用 |
| **正确做法** | 使用 `@require_role(["pitcher"])` 装饰器 |
| **检测方法** | 用非授权角色调用接口 |
| **预防措施** | 每个接口必须标注允许角色 |

#### 错误 #5：状态直接 UPDATE

| 项目 | 内容 |
|------|------|
| **错误示范** | `UPDATE reports SET status='locked'` |
| **正确做法** | 通过状态机服务变更 |
| **检测方法** | `grep -r "UPDATE.*status"` |
| **预防措施** | 状态字段设为只读，只能通过服务变更 |

#### 错误 #6：迁移不可回滚

| 项目 | 内容 |
|------|------|
| **表现** | `downgrade` 函数为空或报错 |
| **正确做法** | 每个迁移必须实现 downgrade |
| **检测方法** | `alembic downgrade -1` 执行成功 |
| **预防措施** | CI 自动测试迁移回滚 |

#### 错误 #7：忘记事务

| 项目 | 内容 |
|------|------|
| **表现** | 多表操作部分成功部分失败 |
| **正确做法** | 使用 `async with session.begin()` |
| **检测方法** | 中断操作检查数据一致性 |
| **预防措施** | 财务操作必须在事务中 |

#### 错误 #8：缺少错误处理

| 项目 | 内容 |
|------|------|
| **表现** | 错误时返回 500 无详情 |
| **正确做法** | 捕获异常返回友好错误码 |
| **检测方法** | 故意传错误参数看响应 |
| **预防措施** | 使用统一异常处理中间件 |

#### 错误 #9：不看 SoT 就写代码

| 项目 | 内容 |
|------|------|
| **表现** | 实现与规范不符 |
| **正确做法** | 先查 BUSINESS_RULES.md |
| **检测方法** | 代码审查对比 SoT |
| **预防措施** | 提示词模板强制引用 SoT |

#### 错误 #10：一次提交太多

| 项目 | 内容 |
|------|------|
| **表现** | 一个 commit 改了 50 个文件 |
| **正确做法** | 每个功能点一个 commit |
| **检测方法** | `git log --stat` 检查 |
| **预防措施** | 遵循"2小时原则"拆分任务 |
