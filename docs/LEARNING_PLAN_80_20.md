## 1. 3-5条最少必备核心知识

### 核心知识清单（覆盖80%应用场景）

#### 1️⃣ **双账本架构（Dual-Ledger）**
- **PROJECT账本**：记录项目收入（客户充值、粉数计费）
- **SUPPLIER账本**：记录供应商成本（供应商充值、真实消耗）
- **核心规则**：两个账本完全独立，禁止混合

#### 2️⃣ **三数据流分离（Triple-Stream）**
- **Raw流**：投手提交的原始数据（`conversions_raw`, `raw_spend`），仅用于趋势风控，永不计费
- **Real流**：运营录入的真实消耗（`real_spend`），用于成本核算
- **Final流**：运营确认的最终粉数（`conversions_final`），用于计费
- **核心规则**：单向流动，禁止从final反推raw

#### 3️⃣ **8状态机强制流转（State Machine）**
- **标准路径**：`null → raw_submitted → trend_pending → trend_ok → final_pending → final_confirmed → final_locked`
- **异常路径**：`trend_pending → trend_flagged → trend_resolved → final_pending`
- **核心规则**：状态=权限边界=账务触发条件，终态`final_locked`后数据冻结

#### 4️⃣ **审计不可逆机制（Immutable Audit Trail）**
- **余额计算**：`余额 = SUM(所有ledger_entries.amount)`
- **禁止操作**：禁止UPDATE/DELETE任何ledger_entries记录
- **修正方式**：唯一方式=REVERSAL（红冲），产生反向事件
- **数学不变量**：`净值 = SUM(原事件) + SUM(REVERSAL事件)`

#### 5️⃣ **SoT文档体系与裁判链（Single Source of Truth）**
- **文档优先级**：MASTER.md > STATE_MACHINE.md > DATA_SCHEMA.md > LEDGER_SOT.md > ...
- **核心规则**：所有代码实现必须基于SoT文档，禁止自创字段/状态/API
- **冲突解决**：高优先级文档覆盖低优先级文档

## 2. 核心知识重要性解释

### 1️⃣ 双账本架构的重要性

**为什么必须理解？**
- **80%的财务问题**都源于账本混淆（收入与成本混记）
- **所有计费逻辑**都基于双账本分离（PROJECT计收入，SUPPLIER计成本）
- **对账功能**完全依赖双账本独立核算
- **死号迁移**需要同时操作两个账本（TRANSFER_OUT/TRANSFER_IN）

**实际应用场景**：
- 开发日报计费功能 → 必须知道PROJECT账本记录REVENUE
- 开发成本核算功能 → 必须知道SUPPLIER账本记录COST
- 开发对账功能 → 必须知道两个账本独立核算
- 修复账务错误 → 必须知道红冲需要同时操作两个账本

### 2️⃣ 三数据流分离的重要性

**为什么必须理解？**
- **80%的数据流转问题**都源于数据流混淆（用raw计费、用final反推raw）
- **所有日报审核流程**都基于三数据流分离
- **风控系统**完全依赖Raw流（趋势检查）
- **计费系统**完全依赖Final流（粉数确认）

**实际应用场景**：
- 开发日报提交功能 → 必须知道投手只能提交Raw数据
- 开发审核功能 → 必须知道运营录入Real、确认Final
- 开发计费功能 → 必须知道只能用Final数据计费
- 开发风控功能 → 必须知道只能用Raw数据做趋势检查

### 3️⃣ 8状态机强制流转的重要性

**为什么必须理解？**
- **80%的权限问题**都源于状态机理解错误（越权操作、跳过状态）
- **所有业务流转**都基于状态机（日报、充值、对账）
- **账务触发**完全依赖状态流转（final_locked后才计费）
- **审计追溯**完全依赖状态变更记录

**实际应用场景**：
- 开发日报审核 → 必须知道状态流转路径和前置条件
- 开发权限控制 → 必须知道状态=权限边界
- 开发计费触发 → 必须知道final_locked后才触发
- 修复状态错误 → 必须知道禁止跳过状态、禁止逆转

### 4️⃣ 审计不可逆机制的重要性

**为什么必须理解？**
- **80%的账务错误修复**都依赖红冲机制
- **所有余额计算**都基于不可变账本（SUM(ledger_entries)）
- **审计合规**完全依赖不可变审计链
- **错误修正**唯一方式=REVERSAL（禁止直接修改）

**实际应用场景**：
- 开发余额查询 → 必须知道余额=SUM(ledger_entries.amount)
- 开发红冲功能 → 必须知道REVERSAL的符号规则（REVENUE红冲=负值，COST红冲=正值）
- 修复账务错误 → 必须知道禁止UPDATE/DELETE，只能用REVERSAL
- 开发审计报表 → 必须知道所有操作都有审计日志

### 5️⃣ SoT文档体系与裁判链的重要性

**为什么必须理解？**
- **80%的代码错误**都源于不遵循SoT文档（自创字段/状态/API）
- **所有开发工作**都必须先查SoT文档（禁止自创）
- **文档冲突解决**完全依赖裁判链优先级
- **代码审查**完全依赖SoT文档对齐

**实际应用场景**：
- 开发新功能 → 必须先查SoT文档（STATE_MACHINE、DATA_SCHEMA、API_SOT）
- 修复Bug → 必须先查SoT文档确认正确行为
- 解决文档冲突 → 必须知道裁判链优先级（MASTER.md > STATE_MACHINE.md > ...）
- 代码审查 → 必须检查是否遵循SoT文档

## 3. 新手常陷入的低效学习误区

### ❌ 误区1：从代码开始，忽略文档

**错误做法**：
- 直接看`backend/routers/`下的代码
- 直接看`frontend/app/`下的页面
- 忽略`docs/2.sot/`下的SoT文档

**为什么低效？**
- 代码是"怎么做"，文档是"为什么这样做"
- 不理解业务规则就写代码，80%会写错
- 代码可能过时，SoT文档是唯一真相源

**正确做法**：
1. 先读`docs/1.overview/MASTER.md`（系统宪法）
2. 再读`docs/2.sot/STATE_MACHINE.md`（状态机）
3. 再读`docs/2.sot/DATA_SCHEMA.md`（数据结构）
4. 最后看代码实现

### ❌ 误区2：试图理解所有细节，陷入完美主义

**错误做法**：
- 想一次性理解所有13个SoT文档
- 想一次性理解所有状态机（日报、充值、对账、转账...）
- 想一次性理解所有业务规则（BR-001到BR-XXX）

**为什么低效？**
- 80%的业务场景只需要理解20%的核心知识
- 细节可以在实际开发中逐步学习
- 完美主义导致"分析瘫痪"，无法开始实践

**正确做法**：
1. 先掌握5条核心知识（双账本、三数据流、状态机、审计不可逆、SoT体系）
2. 在实际开发中遇到具体问题再查具体文档
3. 边做边学，逐步深入

### ❌ 误区3：只看前端或只看后端，忽略全栈视角

**错误做法**：
- 前端开发者只看`frontend/`，忽略后端API
- 后端开发者只看`backend/`，忽略前端交互
- 不理解数据如何从前端流向后端再流向数据库

**为什么低效？**
- 80%的Bug都源于前后端理解不一致
- 不理解全栈流程，无法独立开发完整功能
- 无法理解状态机如何驱动UI变化

**正确做法**：
1. 理解完整数据流：前端表单 → API请求 → 后端Service → 数据库
2. 理解状态机如何驱动UI：状态变更 → API响应 → 前端状态更新
3. 理解权限控制如何贯穿全栈：前端按钮隐藏 → API权限检查 → 数据库RLS

## 4. 可延迟学习的概念

### ⏸️ 可延迟概念1：AI Agent层（docs/6.agent-layer/）

**延迟原因**：
- AI Agent层是"锦上添花"的功能，不是核心业务
- 80%的业务场景不涉及AI Agent
- 理解核心业务逻辑（账本、状态机）更重要

**暂不学习的影响**：
- ✅ 不影响开发日报、充值、对账等核心功能
- ✅ 不影响理解双账本、三数据流、状态机
- ❌ 无法开发AI监控、AI预警等高级功能
- ❌ 无法理解Agent编排流程

**何时学习**：
- 核心业务逻辑完全掌握后
- 需要开发AI功能时
- 需要理解Agent协议时

### ⏸️ 可延迟概念2：OpenSpec变更管理流程（openspec/）

**延迟原因**：
- OpenSpec是"规范变更管理"机制，不是核心业务
- 80%的开发工作不需要修改SoT文档
- 新手只需要"遵循SoT"，不需要"修改SoT"

**暂不学习的影响**：
- ✅ 不影响阅读和理解SoT文档
- ✅ 不影响基于SoT文档开发功能
- ❌ 无法修改SoT文档（需要走OpenSpec流程）
- ❌ 无法创建新的业务规则

**何时学习**：
- 需要修改SoT文档时（新增状态、修改状态机）
- 需要创建新的业务规则时
- 需要提交RFC时

### ⏸️ 可延迟概念3：基础设施层细节（docs/5.infrastructure/）

**延迟原因**：
- CI/CD、监控、日志等是"运维层面"的知识
- 80%的开发工作不涉及基础设施
- 本地开发环境已经配置好，不需要理解部署细节

**暂不学习的影响**：
- ✅ 不影响本地开发（后端、前端）
- ✅ 不影响理解业务逻辑
- ❌ 无法部署到生产环境
- ❌ 无法配置CI/CD流水线

**何时学习**：
- 需要部署到生产环境时
- 需要配置CI/CD时
- 需要排查生产环境问题时

## 5. 生活化类比解释

### 🏦 双账本架构 = 银行的双账户系统

**类比**：
- **PROJECT账本** = 你的"收入账户"（工资卡）
  - 客户充值 = 老板发工资
  - 粉数计费 = 你提供服务赚的钱
  - 余额 = 你赚了多少钱

- **SUPPLIER账本** = 你的"支出账户"（信用卡）
  - 供应商充值 = 你往信用卡里存钱
  - 真实消耗 = 你实际花的钱
  - 余额 = 你花了多少钱

- **为什么分开？** = 就像你不会把工资和信用卡账单混在一起算，收入归收入，支出归支出，才能算清楚"净利润"

### 📊 三数据流分离 = 餐厅的三层审核

**类比**：
- **Raw流** = 服务员写的"点菜单"（可能有错别字、涂改）
  - 投手提交 = 服务员写菜单
  - 用途 = 给厨师看个大概，但不能直接收钱

- **Real流** = 厨师做的"实际菜品"（真实消耗）
  - 运营录入 = 厨师确认实际用了多少食材
  - 用途 = 算成本（用了多少食材）

- **Final流** = 收银台确认的"最终账单"（客户实际付的钱）
  - 运营确认 = 收银台确认客户实际付了多少钱
  - 用途 = 算收入（收了多少钱）

- **为什么分开？** = 就像餐厅不会用"点菜单"直接收钱，必须经过"实际菜品"和"最终账单"两层审核，防止服务员写错导致多收或少收

### 🔄 8状态机强制流转 = 快递的8个配送阶段

**类比**：
- **raw_submitted** = 你下单了（投手提交日报）
- **trend_pending** = 快递公司收到订单（系统检查趋势）
- **trend_ok** = 订单正常（趋势检查通过）
- **trend_flagged** = 订单异常（趋势检查失败，需要人工审核）
- **trend_resolved** = 异常已解决（人工审核通过）
- **final_pending** = 等待配送（运营录入真实数据）
- **final_confirmed** = 已确认收货（运营确认最终数据）
- **final_locked** = 订单完成，不可退款（数据锁定，触发计费）

- **为什么不能跳过？** = 就像快递不能从"下单"直接跳到"已收货"，必须经过"发货"、"运输"、"派送"等阶段，每个阶段都有不同的责任人和权限

### 🔒 审计不可逆机制 = 银行的流水记录

**类比**：
- **ledger_entries** = 银行的"流水记录"（每笔交易都有记录）
- **余额计算** = 余额 = 所有流水记录的SUM（就像银行不会直接存一个"余额"数字，而是通过流水记录计算）
- **禁止UPDATE/DELETE** = 就像银行不能"修改"或"删除"历史流水记录
- **REVERSAL（红冲）** = 如果发现错误，不是"修改"原记录，而是"新增"一条反向记录（就像银行退款不是删除原交易，而是新增一条退款交易）

- **为什么不可逆？** = 就像银行流水记录是"审计证据"，如果允许修改，就无法追溯"谁在什么时候做了什么"，审计就失效了

### 📚 SoT文档体系 = 法律的"宪法-法律-法规"体系

**类比**：
- **MASTER.md** = "宪法"（最高优先级，系统架构宪法）
- **STATE_MACHINE.md** = "法律"（状态机定义，必须遵循）
- **DATA_SCHEMA.md** = "行政法规"（数据结构定义）
- **API_SOT.md** = "部门规章"（API定义）

- **裁判链优先级** = 就像"宪法 > 法律 > 行政法规 > 部门规章"，如果冲突，以高优先级为准
- **禁止自创** = 就像你不能"自创法律"，必须遵循已有的法律体系

   SELECT * FROM ledger_entries WHERE category = 'PROJECT' LIMIT 10;

   SELECT * FROM ledger_entries WHERE category = 'SUPPLIER' LIMIT 10;

## 7. 顶尖高手与普通人的最大区别

### 🎯 核心原则：**"先查SoT，再写代码"**

**普通人的做法**：
1. 看到需求 → 直接写代码
2. 遇到问题 → 查Stack Overflow
3. 代码能跑 → 提交PR
4. **结果**：代码可能违反业务规则，需要反复修改

**顶尖高手的做法**：
1. 看到需求 → 先查SoT文档（STATE_MACHINE、DATA_SCHEMA、API_SOT）
2. 理解业务规则 → 确认状态流转、数据结构、API契约
3. 设计实现方案 → 确保遵循SoT文档
4. 写代码 → 代码即文档，注释引用SoT文档编号
5. **结果**：代码一次通过，符合业务规则，易于维护

### 💡 为什么这是最大区别？

**1. 避免80%的错误**
- 80%的Bug都源于不遵循SoT文档（自创字段/状态/API）
- 先查SoT，就能避免这些错误

**2. 提高开发效率**
- 不需要"猜测"业务规则，SoT文档是唯一真相源
- 不需要"反复修改"，一次写对

**3. 保证代码质量**
- 代码符合业务规则，易于测试
- 代码易于维护，新成员也能快速理解

**4. 建立系统思维**
- 理解"为什么这样做"，而不只是"怎么做"
- 理解系统架构，而不只是代码实现

### 🚀 如何培养这个习惯？

**第一步：建立检查清单**
- 开发新功能前，先问自己：
  1. 这个功能涉及哪些状态？→ 查`STATE_MACHINE.md`
  2. 需要哪些数据字段？→ 查`DATA_SCHEMA.md`
  3. API应该怎么设计？→ 查`API_SOT.md`
  4. 权限如何控制？→ 查`AUTH_SPEC.md`

**第二步：代码注释引用SoT**
- 在代码中注释SoT文档编号，例如：
  ```python
  # 状态流转规则：STATE_MACHINE.md §8.1
  # 禁止跳过状态：MASTER.md §INV-003
  if current_state != 'final_pending':
      raise InvalidStateTransition()
  ```

**第三步：代码审查时检查SoT对齐**
- 提交PR前，检查代码是否遵循SoT文档
- 如果发现冲突，优先修改代码，而不是修改SoT
