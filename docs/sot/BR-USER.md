## 规则详细定义

### BR-USER-001: 角色枚举固定

#### 业务场景
系统角色是权限控制的基础，必须严格限制在预定义的 6 个业务角色范围内。任何新增、修改角色的需求必须通过 SoT 文档变更流程，禁止代码层面随意添加角色。

#### 详细约束
- 📌 **强制**: 系统仅允许 6 个业务角色（PRD v2.2）
- ❌ **禁止**: 使用已废弃的 `supervisor` 角色
- ❌ **禁止**: 在代码中添加白名单外的新角色
- ❌ **禁止**: 使用角色数组或多角色设计
- ✅ **允许**: 通过 SoT 变更流程新增角色（需 PM 和架构师审批）

#### 业务层 6 角色定义

| 角色代码 | 业务名称 | 权限级别 | 核心职责 | 可见范围 |
|---------|---------|---------|---------|---------|
| `ceo` | 老板 | L6 (最高) | 资金安全、公司盈亏、最终决策 | 全部可见 |
| `project_owner` | 项目负责人 | L5 | 项目盈亏、日报审核、资金使用效率 | 自己项目 |
| `finance` | 财务 | L4 | 资金出入准确、数据真实、对账 | 充值/账本/对账 |
| `pitcher` | 投手 | L3 | CPL 达标、日报准确、执行投放 | 仅自己日报和账户 |
| `account_manager` | 户管 | L2 | 账户分配、账户状态监控 | 仅账户管理 |
| `admin` | 管理员 | L1 | 系统配置（不参与业务） | 全部可见 |

#### 技术层映射

| 业务角色 | 技术层枚举 | 说明 |
|---------|-----------|------|
| ceo | `admin` | 老板使用 admin 权限 |
| project_owner | `is_project_owner=true` | 业务属性（非枚举角色） |
| finance | `finance` | 保持不变 |
| pitcher | `media_buyer` | 技术名保持兼容 |
| account_manager | `account_manager` | 保持不变 |
| admin | `admin` | 保持不变 |

#### 前置条件
- 数据状态: 用户创建或角色变更时
- 引用: MASTER.md v4.6 §2.4, AUTH_SPEC.md v2.2 §2.2

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 使用无效角色 | `BIZ_001` | 400 | 无效的角色类型 |
| 使用已废弃角色 | `BIZ_001` | 400 | supervisor 角色已废弃 |
| 角色不在白名单 | `BIZ_001` | 400 | 角色必须在白名单范围内 |

#### 代码引用
- Model: `backend/models/user.py`
- 字段: `role VARCHAR(20) CHECK (role IN ('admin', 'finance', 'account_manager', 'media_buyer'))`
- 字段: `is_project_owner BOOLEAN DEFAULT FALSE`  -- 项目负责人标记

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | 创建有效角色用户 | role=pitcher | 成功 |
| T2 | 使用无效角色 | role=superuser | `BIZ_001` |
| T3 | 使用已废弃角色 | role=supervisor | `BIZ_001` |
| T4 | 创建 ceo 用户 | role=ceo (映射 admin) | 成功 |

### BR-USER-002: 角色不可为空

#### 业务场景
每个用户必须分配一个有效角色，角色决定了用户的权限范围和可见数据。无角色用户将无法访问任何业务功能。

#### 详细约束
- 📌 **强制**: `users.role` 字段 NOT NULL
- 📌 **强制**: 创建用户时必须指定角色
- ❌ **禁止**: 将角色设为空字符串或 null
- ❌ **禁止**: 删除用户角色而不分配新角色
- ✅ **允许**: 角色变更（旧角色 → 新角色，必须原子操作）

#### 前置条件
- 数据状态: 用户创建或更新时
- 引用: DATA_SCHEMA.md v5.6 §3.1.1

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 角色字段为空 | `VALIDATION_001` | 400 | 角色不能为空 |
| 角色字段为 null | `VALIDATION_001` | 400 | 角色不能为空 |
| 创建用户未指定角色 | `VALIDATION_001` | 400 | 必须指定用户角色 |

#### 代码引用
- Model: `backend/models/user.py`
- Schema: `backend/schemas/user.py`
- 字段: `role: str = Field(..., description="用户角色")`

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | 创建有角色用户 | role=finance | 成功 |
| T2 | 角色为空字符串 | role="" | `VALIDATION_001` |
| T3 | 角色为 null | role=null | `VALIDATION_001` |
| T4 | 更新时删除角色 | role=null (UPDATE) | `VALIDATION_001` |

### BR-USER-003: 角色变更审计

#### 业务场景
角色变更是高风险操作，会导致权限范围变化。所有角色变更必须记录完整的审计日志，包括操作人、变更前后状态、时间戳和 IP 地址。

#### 详细约束
- 📌 **强制**: 角色变更必须记录到 `audit_logs` 表
- 📌 **强制**: 审计日志包含：操作人、变更前角色、变更后角色、时间戳、IP
- 📌 **强制**: 仅 `admin` 或 `ceo` 可执行角色变更
- ❌ **禁止**: 直接 UPDATE 数据库绕过审计
- ✅ **允许**: 通过 API 执行角色变更（自动记录审计）

#### 审计日志字段
| 字段 | 类型 | 说明 |
|------|------|------|
| module | VARCHAR | 固定为 "users" |
| action | VARCHAR | 固定为 "role_change" |
| entity_id | VARCHAR | 被修改用户的 ID |
| performed_by | UUID | 操作人 ID |
| role | VARCHAR | 操作人角色 |
| ip_address | INET | 操作人 IP |
| payload_before | JSONB | `{"role": "旧角色"}` |
| payload_after | JSONB | `{"role": "新角色", "reason": "变更原因"}` |

#### 前置条件
- 用户角色: 操作人必须是 `admin` 或 `ceo`
- 数据状态: 被修改用户存在
- 引用: AUTH_SPEC.md v2.2 §8, DATA_SCHEMA.md v5.6 §3.1.4

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 非 admin 执行角色变更 | `AUTH_500` | 403 | 仅管理员可修改用户角色 |
| 审计日志写入失败 | `SYS_001` | 500 | 系统内部错误 |
| 被修改用户不存在 | `BIZ_002` | 404 | 用户不存在 |

#### 代码引用
- Service: `backend/services/user_service.py`
- 方法: `update_user_role()`

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | admin 修改角色 | admin 操作 | 成功 + 审计日志 |
| T2 | 非 admin 修改角色 | finance 操作 | `AUTH_500` |
| T3 | 验证审计日志完整 | 查询 audit_logs | 包含完整字段 |
| T4 | 被修改用户不存在 | user_id=无效 | `BIZ_002` |

### BR-USER-004: 禁止自我提权

#### 业务场景
用户不得修改自己的角色，防止权限越界和内部欺诈。角色变更必须由其他管理员执行，确保双人复核。

#### 详细约束
- 📌 **强制**: 用户不能修改自己的 `role` 字段
- 📌 **强制**: API 层校验 `current_user.id ≠ target_user.id`
- ❌ **禁止**: 任何用户（包括 admin）修改自己的角色
- ✅ **允许**: admin A 修改 admin B 的角色（需审计）
- ✅ **允许**: ceo 指定其他用户为 ceo

#### 前置条件
- 用户角色: 操作人必须是 `admin` 或 `ceo`
- 数据状态: 操作人 ID ≠ 目标用户 ID
- 引用: AUTH_SPEC.md v2.2 §5.1.2

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| 修改自己的角色 | `AUTH_500` | 403 | 禁止修改自己的角色 |
| 自我提权尝试 | `AUTH_500` | 403 | 禁止自我提权 |

#### 代码引用
- Service: `backend/services/user_service.py`
- 方法: `update_user_role()`

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | admin 修改他人角色 | admin A → user B | 成功 |
| T2 | admin 修改自己角色 | admin A → admin A | `AUTH_500` |
| T3 | 普通用户自我提权 | pitcher → pitcher | `AUTH_500` |
| T4 | ceo 修改他人为 ceo | ceo A → user B | 成功 |

### BR-USER-005: admin 角色限制

#### 业务场景
`admin` 角色是系统管理员，主要负责系统配置和用户管理，不应参与日常业务操作（如提交日报、申请充值）。这确保了职责分离和审计清晰。

#### 详细约束
- 📌 **强制**: admin 仅用于系统配置操作
- ❌ **禁止**: admin 提交日报（业务操作）
- ❌ **禁止**: admin 申请充值（业务操作）
- ✅ **允许**: admin 强制审核/审批（需填写原因 + 审计）
- ✅ **允许**: admin 查看所有数据（监控目的）
- ✅ **允许**: admin 管理用户和系统配置

#### admin 允许的操作
| 操作类型 | 允许 | 说明 |
|---------|------|------|
| 用户管理 | ✅ | 创建/编辑/禁用用户 |
| 角色变更 | ✅ | 修改用户角色 |
| 系统配置 | ✅ | 配置系统参数 |
| 数据查看 | ✅ | 查看所有业务数据 |
| 强制审核 | ✅ | 绕过 SOD（需原因） |
| 提交日报 | ❌ | 业务操作 |
| 申请充值 | ❌ | 业务操作 |
| 正常审核 | ✅ | 作为审核者（非绕过） |

#### 前置条件
- 用户角色: `admin`
- 引用: MASTER.md v4.6 §2.4, AUTH_SPEC.md v2.2 §5.1.1

#### 错误码映射
| 违反场景 | 错误码 | HTTP | 错误消息 |
|----------|--------|------|----------|
| admin 提交日报 | `BIZ_001` | 400 | 管理员不得参与业务操作 |
| admin 申请充值 | `BIZ_001` | 400 | 管理员不得参与业务操作 |

#### 代码引用
- Service: `backend/services/daily_report_service.py`
- 方法: `create_report()` 中的角色校验

#### Test Intent
| ID | 测试场景 | 输入 | 预期结果 |
|----|----------|------|----------|
| T1 | admin 查看日报 | GET /daily-reports | 成功 |
| T2 | admin 提交日报 | POST /daily-reports | `BIZ_001` |
| T3 | admin 创建用户 | POST /users | 成功 |
| T4 | admin 强制审核 | force_approve + reason | 成功 + 审计 |
