# MASTER.md 重构方案

> 目标：基于已校准的业务流程，重构 MASTER.md 使其成为系统设计的最高真相源
> 日期：2025-12-22
> 依据：BUSINESS_FLOW_MANAGEMENT.md, MVP_PHASE_DESIGN.md

---

## 一、当前 MASTER.md 的主要问题诊断

### 1.1 偏「理想系统」而非「现实业务」

| 问题 | 当前 MASTER | 现实业务 |
|------|-------------|----------|
| 核心假设 | 所有账务必须源于日报（BI-04） | 数据来自 Excel，历史不完美 |
| 数据一致性 | 假设数据一致，强制校验 | 存在人工裁决、数据不一致 |
| 手续费 | 假设 `cost = real_spend × (1 + fee_rate)` | 手续费不总是可计算 |
| 回款 | 未涉及 | 存在延迟回款、跨项目预付款 |

### 1.2 与现实业务流程脱节

| 维度 | 当前 MASTER | 业务流程实际 |
|------|-------------|--------------|
| 核心关切 | 状态机流转、账务不可逆 | 谁对钱负责、谁对结果负责 |
| 角色定义 | pitcher, supervisor, finance, ceo, admin | 缺少「项目负责人」这一关键角色 |
| 责任归属 | 按角色分权限 | 按「资金链/结果链/纠偏链」分责任 |
| 系统目标 | 防止账务风险 | 支撑老板决策 |

### 1.3 容易导致 AI 幻觉或过度自动化

```
当前 MASTER 的问题：
├── INV-001 至 INV-004 的「禁止条款」过于绝对
│   → AI 可能生成「自动拒绝」「自动阻断」的代码
│
├── 没有 Phase 1 / Phase 2 的区分
│   → AI 不知道哪些功能在 MVP 阶段应该「软性提示」而非「强制阻断」
│
├── 「禁止 Excel 导入自动生成 entry」（D-02）
│   → 但实际上 Excel 是主要数据来源
│
└── 假设「所有角色不得绕过状态机」
    → 但 Phase 1 的原则是「可绕行，有记录」
```

### 1.4 缺少管理视角

**老板真正关心的三个问题：**
1. 钱在哪里？（资金安全）
2. 项目赚钱吗？（盈亏）
3. 出了问题找谁？（责任）

**当前 MASTER 的回答：**
- ❌ 没有直接回答这三个问题
- ❌ 开篇是「双账本」「三数据流」「状态机」等技术概念
- ❌ 老板读不懂，开发者也容易误解系统目标

## 二、基于业务流程的 MASTER.md 重构原则

### 原则 1：以「管理责任」为核心，而非「技术机制」

```
原来的开篇：
"AI 广告代投系统管理三方资金流转..."

重构后的开篇：
"本系统的唯一目标是：支撑老板决策。
核心管理目标：谁对钱负责、谁对结果负责、谁能纠偏。"
```

### 原则 2：明确区分「业务事实」「管理状态」「管理裁决」

| 类型 | 定义 | 系统责任 | 示例 |
|------|------|----------|------|
| **业务事实** | 客观发生的事 | 必须记录 | 消耗、进粉、充值申请 |
| **管理状态** | 计算或判断的结果 | 展示 | CPL、毛利、异常标记 |
| **管理裁决** | 需要人决定的事 | 不替代 | 批准/拒绝、继续/终止 |

### 原则 3：显式体现 Phase 1 / Phase 2 边界

```
Phase 1（照亮）：
├── 系统记录事实
├── 系统展示状态
├── 系统提示异常
└── 不强制阻断

Phase 2（问责）：
├── 引入约束（无批准不打款）
├── 强制审批（必须审核）
└── 考核关联（绩效扣分）
```

### 原则 4：接受数据现实，不假设理想状态

```
必须接受的现实：
├── 数据来自 Excel，历史不完美
├── 存在人工裁决和延迟回款
├── 手续费不总是可计算
├── 预付款可能跨项目使用
└── 系统目标是「照亮问题」，不是「消灭问题」
```

### 原则 5：约束 AI 编码边界

```
AI 禁止假设：
├── 数据一定一致
├── 钱一定可算
├── 项目一定可控
└── 系统可以替代人判断
```

## 四、关键章节的优化要点与示例说明

### 4.1 第一章 系统目标与管理原则（核心重写）

**原文开篇：**
```
AI 广告代投系统管理三方资金流转：
- 客户 → 充值至项目账户 → 按粉数计费扣款
- 平台 → 管理项目账本（收入侧）与供应商账本（成本侧）
- 供应商 → 接收充值 → 按真实消耗扣款
```

**优化后开篇：**
```markdown
## 第一章 系统目标与管理原则（老板视角）

### 1.1 系统的唯一目标

本系统的唯一目标是：**支撑老板决策，而不是替代人做判断**。

系统是「工具」，用于：
- 记录事实（消耗、充值、审批）
- 展示状态（盈亏、CPL、异常）
- 提示风险（超标、亏损、超预算）

系统不是「裁判」，不替代人做：
- 继续/调整/终止 的决策
- 批准/拒绝 的判断
- 追责/处罚 的裁决

### 1.2 核心管理目标（三权清晰）

┌────────────────────────────────────────────────────────────────┐
│                       三权清晰                                 │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  【谁对钱负责】                                                │
│  ├── 项目负责人：申请充值，对使用效率负责                      │
│  ├── 财务：审核合规，守住资金出口                              │
│  └── 老板：最终批准，承担资金风险                              │
│                                                                │
│  【谁对结果负责】                                              │
│  ├── 投手：对每日 CPL 达标负责                                 │
│  ├── 主管：对团队产出负监督责任                                │
│  └── 项目负责人：对项目盈亏负责                                │
│                                                                │
│  【谁能在过程中纠偏】                                          │
│  ├── 日级：主管看日报 → 发现异常 → 沟通调整                   │
│  ├── 周级：项目负责人看盈亏 → 提前预警                        │
│  ├── 月级：老板确认结算 → 继续/调整/终止                      │
│  └── 随时：老板发现重大异常 → 冻结/终止                       │
│                                                                │
└────────────────────────────────────────────────────────────────┘

### 1.3 系统定位

管理责任必须先落实，系统只是让责任更清晰。

| 管理目标 | 系统如何支撑 | 系统不做什么 |
|----------|-------------|-------------|
| 钱有负责人 | 记录每笔充值申请与审批 | 不替老板批准/拒绝 |
| 结果有责任人 | 展示项目盈亏与负责人 | 不替老板追责 |
| 风险可纠偏 | 高亮异常、生成报表 | 不自动暂停/冻结 |
```

**可直接使用的内容：**

```markdown
## 第三章 Phase 1 / Phase 2 执行边界

### 3.1 Phase 1（照亮）

**目标**：让问题「可见」，而不是「问责」

**原则**：
| 原则 | 说明 | 系统禁止 |
|------|------|----------|
| 可见优先 | 数据透明，老板能看到问题 | 不允许系统自动惩罚 |
| 解释责任 | 责任人需解释数据，但不追责 | 不允许因亏损直接问责 |
| 软性提醒 | 异常只高亮提示，不阻断流程 | 不允许自动冻结/停项目 |
| 人工裁决 | 所有重要决策由人做出 | 不允许系统替代人判断 |

**系统能做**：
- ✓ 记录充值申请与审批流程
- ✓ 高亮异常数据（CPL 超标、消耗突增）
- ✓ 生成周度/月度汇总报表
- ✓ 展示项目盈亏与责任人

**系统不能做**：
- ✗ 自动拒绝充值申请
- ✗ 自动暂停投手账户
- ✗ 自动冻结项目
- ✗ 强制要求填写周报

### 3.2 Phase 2（问责）

**相比 Phase 1 新增的约束**：
| 功能 | Phase 1 | Phase 2 |
|------|---------|---------|
| 充值审批 | 可绕行 | 无批准不打款 |
| 日报审核 | 可选 | 必须审核 |
| 周度简报 | 可选提交 | 必须提交 |
| 异常处理 | 提示 | 暂停建议 |
| 结算锁定 | 可修改 | 锁定不可改 |

**Phase 2 启动前提**：
1. Phase 1 已稳定运行至少 2 个月
2. 日报填报率 > 90%
3. 周报提交率 > 80%
4. 团队对责任划分无重大异议
```

### 4.5 第七章 AI 编码防幻觉原则（新增章节）

**可直接使用的内容：**

```markdown
## 第七章 AI 编码防幻觉原则

### AH-01: 禁止假设数据一致

**禁止**：
- AI 不得假设「系统消耗 = 代理商账单」
- AI 不得假设「所有项目有预算」
- AI 不得假设「所有账户有分配投手」

**必须**：
- 遇到数据缺失，标记为「待人工确认」
- 遇到数据不一致，展示差异而非强制校验
- 允许字段为空，不强制 NOT NULL

### AH-02: 禁止自动做管理裁决

**禁止**：
- AI 不得生成「自动拒绝充值申请」的代码
- AI 不得生成「自动暂停投手账户」的代码
- AI 不得生成「自动终止项目」的代码

**必须**：
- 所有「决策」场景，展示信息 + 等待人操作
- 最多生成「建议」，不生成「强制」
- Phase 1 的所有约束都是「提示」而非「阻断」

### AH-03: 禁止引入 SoT 未定义的概念

**禁止**：
- AI 不得创建 DATA_SCHEMA 未定义的字段
- AI 不得创建 MVP_PHASE_DESIGN 未定义的页面
- AI 不得创建 ERROR_CODES_SOT 未定义的错误码

**必须**：
- 发现 SoT 缺失，停止生成代码
- 标注缺失信息，询问用户
- 不自行补充「合理推测」

### AH-04: 必须遵循 Phase 1 软性原则

**禁止**：
- 在 Phase 1 代码中实现「强制阻断」
- 在 Phase 1 代码中实现「自动惩罚」
- 在 Phase 1 代码中实现「必填强制」

**必须**：
- Phase 1 的约束 = 提示 + 高亮 + 记录
- Phase 2 功能用 feature flag 控制，默认关闭
- 阻断功能的代码需注释「Phase 2 启用」

### AH-05: 遇到歧义必须停止并询问

**触发条件**：
```
