# 项目规则总纲（Project Rules Master Spec）

> **版本**: v2.0
> **更新日期**: 2025-01-22
> **文档性质**: 项目级开发规则总纲
> **维护责任**: 项目架构团队

---

## 📋 文档说明

### 本文档定位

本文档是 **AI 广告代投系统的开发规则总纲**，作用为：

- **规则索引中心**：统一指向各 SoT 文档和领域规范
- **冲突仲裁标准**：当不同规范文档冲突时，明确仲裁规则
- **技术决策记录**：记录技术栈选型、架构原则、禁止事项
- **变更流程规范**：定义如何正确修改 SoT、发布变更、审查代码

### 本文档不做什么

- ❌ **不重复业务规则**：字段定义、状态枚举、角色权限、计费逻辑等均在 SoT 文档中定义
- ❌ **不定义实现细节**：具体 API 端点、数据库表结构、状态流转等由各 SoT 文档负责
- ❌ **不列举工具命令**：测试命令、代码格式化等由执行指南文档负责

## ⚖️ 冲突仲裁规则

### 优先级顺序（从高到低）

1. **MASTER_SPEC.md** - 系统架构总纲、全局规则、文档关系
   - 仲裁范围：架构决策、角色定义、主键策略、时间/金额规范
2. **SoT 文档组（Level 0）** - 各领域唯一真相来源
   - DATA_SCHEMA.md - 数据库字段、类型、约束、索引
   - STATE_MACHINE.md - 状态枚举、状态流转规则
   - API_SOT.md - API 端点规范、响应格式
   - AUTH_SPEC.md - 认证流程、Token 生命周期、RBAC
   - LEDGER_SOT.md - 账本架构、entry_type 定义
   - ERROR_CODES_SOT.md - 错误码定义、HTTP 状态码映射
   - BUSINESS_RULES.md - 业务规则索引
3. **本文档（.project-rules.md）** - 开发规则总纲
   - 仲裁范围：开发流程、规则合规、变更管理
4. **领域规范文档（Level 2）** - API、前端开发规则
5. **执行指南（Level 3）** - 开发流程、检查清单
6. **参考文档（Level 4）** - 技术文档、部署指南

| **状态枚举/流转规则** | STATE_MACHINE.md | 修改其他文档以对齐 STATE_MACHINE.md |
| **API 规范/响应格式** | API_SOT.md | 修改其他文档以对齐 API_SOT.md |

## 🎯 核心技术栈（强制约束）

### 后端技术栈

- **框架**: FastAPI 0.104+
- **数据验证**: Pydantic v2 (ConfigDict from_attributes=True)
- **ORM**: SQLAlchemy 2.0+ 同步版本（禁止异步 ORM）
- **数据库**: PostgreSQL 15 (Supabase 托管)
- **迁移**: Alembic 1.12+
- **认证**: JWT + Supabase Auth

### 前端技术栈

- **框架**: Next.js 14+ App Router
- **语言**: TypeScript 严格模式
- **样式**: Tailwind CSS
- **组件库**: shadcn/ui + Radix UI
- **状态管理**: Zustand + React Hooks
- **包管理**: pnpm（禁止 npm/yarn）

### 强制性约束

| 约束 | 说明 | 违规后果 |
|-----|------|---------|
| **禁止修改 models/ 未先查 DATA_SCHEMA.md** | 所有字段必须先在 DATA_SCHEMA.md 定义 | PR 拒绝 |
| **禁止自创状态枚举** | 所有状态值必须在 STATE_MACHINE.md 定义 | PR 拒绝 |
| **禁止自创错误码** | 所有错误码必须在 ERROR_CODES_SOT.md 定义 | PR 拒绝 |
| **禁止自创角色** | 仅 6 个固定角色（ceo/project_owner/finance/pitcher/account_manager/admin） | PR 拒绝 |
| **禁止前端直接解析 JWT Payload** | 必须通过 GET /auth/me 获取用户信息 | PR 拒绝 |

## 📐 开发通用原则

### 1. 命名规范

#### 数据库命名

| 对象 | 规则 | 示例 | 禁止 |
|-----|------|------|-----|
| 表名 | 小写复数 snake_case | users, daily_reports, topup_requests | User, DailyReport |
| 主键 | 固定 id | id | user_id, pk, uid |
| 外键 | &lt;实体名&gt;_id | project_id, user_id | project, userID |
| 布尔字段 | is_*/has_* 前缀 | is_active, has_pending_risk | active |
| 索引 | idx_&lt;表名&gt;_&lt;字段&gt; | idx_users_username | ix_users_1 |

#### 代码命名

| 对象 | 规则 | 示例 | 禁止 |
|-----|------|------|-----|
| Model 类 | PascalCase 单数 | User, DailyReport | user, daily_report |
| Schema 类 | PascalCase + 后缀 | UserCreate, DailyReportUpdate | create_user |
| Service 类 | PascalCase + Service | UserService, DailyReportService | user_service |
| 函数/方法 | snake_case 动词开头 | get_current_user, create_daily_report | getCurrentUser |

### 2. 时间/金额/主键规范

**引用**: MASTER_SPEC.md 第 6 章，DATA_SCHEMA.md 第 1.1 节

| 规则类型 | 强制要求 | 违规检查 |
|---------|---------|---------|
| **时间字段** | TIMESTAMPTZ + NOW() + UTC | 禁止 TIMESTAMP 无时区 |
| **金额字段** | DECIMAL(15,2) + 默认 0.00 + Python Decimal | 禁止 FLOAT |
| **主键策略** | 跨系统实体用 UUID，核心业务表用 BIGSERIAL | 禁止混用类型 |
| **外键一致性** | 外键类型必须与被引用主键完全一致 | 自动检查 |

### 3. 规则合规性原则

| 原则 | 说明 | 强制规则 |
|-----|------|---------|
| **字段不可自创** | 所有字段必须在 DATA_SCHEMA.md 定义 | 开发前必读 SoT |
| **状态不可自创** | 所有状态值必须在 STATE_MACHINE.md 定义 | 禁止脑补状态 |
| **错误码不可自创** | 所有错误码必须在 ERROR_CODES_SOT.md 定义 | 禁止临时错误码 |
| **业务逻辑在 Service 层** | Router 层仅做 Token 验证和参数校验 | 禁止 Router 层实现业务逻辑 |
| **数据权限在 Service 层** | 必须在 Service 层验证数据归属 | 禁止信任前端过滤 |

## 🔄 变更流程规范

### SoT 文档变更流程

```mermaid
flowchart TD
    A[提出变更需求] --> B{涉及 SoT 文档?}
    B -->|是| C[先更新 SoT 文档]
    B -->|否| D[直接开发]
    C --> E[创建 PR 标注 [SoT]]
    E --> F{架构团队审查}
    F -->|拒绝| G[修改 SoT 文档]
    G --> E
    F -->|通过| H[合并 SoT PR]
    H --> I[生成数据库迁移脚本]
    I --> J[开发代码实现]
    J --> K[创建代码 PR]
    K --> L{代码审查}
    L -->|拒绝| M[修改代码]
    M --> K
    L -->|通过| N[合并代码 PR]
    N --> O[运行测试]
    O --> P[部署上线]
```

### 变更规则

| 变更类型 | 必须流程 | 审批权限 | 回归要求 |
|---------|---------|---------|---------|
| **新增字段** | 1. 更新 DATA_SCHEMA.md<br/>2. 生成迁移脚本<br/>3. 更新 Model/Schema<br/>4. 运行测试 | 架构团队 | 全量测试 |
| **新增状态** | 1. 更新 STATE_MACHINE.md<br/>2. 更新白名单<br/>3. 更新 Service 层逻辑<br/>4. 运行测试 | 架构团队 | 状态机测试 |
| **新增 API** | 1. 更新 API_SOT.md<br/>2. 实现 Schema/Service/Router<br/>3. 运行测试 | Tech Lead | API 集成测试 |
| **修改业务规则** | 1. 更新 BUSINESS_RULES.md<br/>2. 修改 Service 层<br/>3. 运行测试 | 产品负责人 | 全量测试 |

### 禁止变更

| 禁止行为 | 说明 | 违规后果 |
|---------|------|---------|
| **直接修改 models/ 未更新 DATA_SCHEMA.md** | 数据库字段必须先在 SoT 文档定义 | PR 自动拒绝 |
| **直接 UPDATE status 未走状态机** | 状态流转必须符合 STATE_MACHINE.md | PR 自动拒绝 |
| **直接修改终态数据** | final_locked 后必须通过红冲修正 | PR 自动拒绝 |
| **跨供应商直接 TRANSFER** | 死号迁移必须拆分为退款 + 充值 | PR 自动拒绝 |

## 🚫 技术决策与禁止事项

### 架构决策

| 决策 | 说明 | 理由 |
|-----|------|------|
| **权限由 Service 层控制** | 数据权限过滤在 Service 层实现 | 前端不可信，必须后端验证 |
| **状态机集成** | 所有状态变更必须符合 STATE_MACHINE.md | 防止非法状态流转 |
| **双账本独立** | PROJECT/SUPPLIER 账本不得混合 | 收入成本独立核算 |
| **终态保护** | final_locked 后仅可红冲 | 防止数据篡改 |
| **RLS 默认关闭** | 当前版本仅应用层 RBAC | 简化开发，未来可启用 |

### 禁止事项（零容忍）

| 禁止行为 | 说明 | 检测方式 |
|---------|------|---------|
| **禁止在 Router 层实现业务逻辑** | Router 层仅做 Token 验证和参数校验 | Code Review |
| **禁止前端直接解析 JWT Payload** | 必须通过 GET /auth/me 获取用户信息 | Code Review |
| **禁止信任前端传递的 user_id** | 必须从 JWT Token 提取 user_id | Code Review |
| **禁止自创字段/状态/错误码** | 必须在 SoT 文档定义 | PR 自动检查 |
| **禁止硬编码敏感信息** | 必须使用环境变量 | 自动扫描 |
| **禁止直接 UPDATE/DELETE 终态数据** | 必须通过红冲机制 | 数据库触发器 |

## 🤖 AI 使用规则

### AI 开发约束

**引用**: CLAUDE.md

| 原则 | 说明 | 强制规则 |
|-----|------|---------|
| **禁止全局性修复任务** | 任务必须明确指向具体文件或模块 | 必须输出计划并等待确认 |
| **必须先查 SoT 文档** | 开发前必须读取相关 SoT 文档 | 禁止脑补字段/状态/错误码 |
| **必须运行验证命令** | 执行后必须报告测试结果 | 禁止不验证直接提交 |
| **禁止泄露敏感信息** | 禁止在日志中输出密码、Token | 自动扫描 |

### AI 开发流程约束

1. **必须先查看 git status/git diff**
2. **必须使用工具发现问题**（ESLint/pytest）
3. **禁止逐文件"肉眼修复"**
4. **必须按"修改内容 + 影响文件 + 验证方式"格式输出**

## 📚 规则使用方法

### 开发前检查清单

- [ ] 阅读 MASTER_SPEC.md 了解系统架构
- [ ] 阅读相关 SoT 文档（DATA_SCHEMA/STATE_MACHINE/API_SOT 等）
- [ ] 确认字段名、状态值、错误码与 SoT 文档一致
- [ ] 确认技术方案符合本文档规范
- [ ] 理解业务需求和权限要求

### 开发中检查清单

- [ ] 遵循命名规范和编码规范
- [ ] 实现权限控制（Service 层数据过滤）
- [ ] 添加错误处理（使用 ERROR_CODES_SOT.md 错误码）
- [ ] 编写测试用例（单元测试 + 集成测试）

### 提交前检查清单

- [ ] 运行所有检查命令并通过（lint/type-check/test/build）
- [ ] 代码审查通过
- [ ] 文档更新完成（如涉及 SoT 变更）
- [ ] Git 提交信息规范（Conventional Commits）

### 如何正确使用 SoT 文档

| 场景 | 使用 SoT 文档 | 禁止行为 |
|-----|-------------|---------|
| **新增数据库字段** | 1. 先在 DATA_SCHEMA.md 定义<br/>2. 生成迁移脚本<br/>3. 更新 Model | 直接修改 Model |
| **新增状态** | 1. 先在 STATE_MACHINE.md 定义<br/>2. 更新白名单<br/>3. 更新 Service 层 | 直接添加状态枚举 |
| **新增 API** | 1. 先在 API_SOT.md 定义<br/>2. 实现 Schema/Service/Router | 直接写代码 |
| **修改业务规则** | 1. 先在 BUSINESS_RULES.md 更新<br/>2. 修改 Service 层 | 直接改代码 |
